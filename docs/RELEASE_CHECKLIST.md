# Чеклист выпуска PR #39 (ТЗ #37, #40)

Порядок для владельца: что проверить до слияния, что сделать на сервере и как откатиться.
Слияние в `main` = обновление сервера: автообновление ставит любой зелёный коммит `main`.

## 1. До слияния

- [ ] Независимый аудит по SHA последнего коммита PR (GPT), замечания закрыты.
- [ ] CI зелёный на последнем коммите: «Lint, typecheck, test, build», «Docker stack
      (compose)», «Docker stack behind Caddy (proxy)», «Disaster drills (backup, restore,
      broken release, rollback)».
- [ ] Включена защита ветки `main` (DEV-1) по `docs/BRANCH_PROTECTION.md`: только через PR,
      четыре обязательные проверки, запрет force-push и удаления, проверка `gh api` прошла.
- [ ] В `deploy/.env` на сервере заданы канал уведомлений (`NOTIFY_*`) и, до реальных
      пользователей, хранилище копий вне сервера (`BACKUP_RCLONE_REMOTE`,
      `BACKUP_AGE_RECIPIENT`).
- [ ] До публичного запуска задан внешний монитор (`MONITOR_HEARTBEAT_URL`, период 1 ч):
      без него падение сервера и недошедшие уведомления никто не увидит; `deploy.sh`
      напоминает об этом в каждом обновлении.
- [ ] На сервере свободно не меньше 5 ГБ (`df -h /`), иначе обновление само почистит кеш сборки.
- [ ] Согласие владельца на слияние («вливай»).

## 2. Что меняется на сервере

Миграции (применяются автоматически, перед ними автоматически делается копия БД):

| Миграция | Что делает | Совместимость со старым кодом на время обновления |
|---|---|---|
| `20261019090000_external_accounts` | таблица привязок банков (уже в `main`, PR #38) | — |
| `20261019100000_job_request_id_bid_job_changed` | `jobs.request_id` (+ уникальный индекс), `bids.job_changed_at` | новые столбцы допускают NULL: старый API их не трогает |
| `20261019110000_job_close_outcome_bid_reject_reason` | два enum, `jobs.close_outcome`, `bids.reject_reason`, заполнение причины у уже отклонённых откликов | новые столбцы допускают NULL |
| `20261019120000_catalog_search_indexes` | `CREATE EXTENSION pg_trgm`, три GIN-индекса, частичный индекс, удаление неиспользуемого индекса | только индексы; построение блокирует запись в `jobs` на доли секунды при текущем объёме |
| `20261019130000_job_request_hash` | `jobs.request_hash` (SHA-256 содержимого заказа для ключа публикации) | столбец допускает NULL; прежний API его не трогает (проверено `schema-compat-test.sh`) |

Новое поведение, которое заметят тестировщики:

- заказ нельзя опубликовать дважды повторной отправкой; повтор с тем же ключом, но другим
  содержимым получает понятный отказ, а не прежний заказ; правка заказа и черновик в двух
  вкладках не затирают друг друга, а предупреждают;
- у откликов пометка «заказ изменён после вашего отклика»; у отклонённых — причина;
- закрытие заказа с исходом: без исполнителя — «Отменить заказ», в работе — «выполнен» или
  «отменён»;
- при истёкшей сессии формы не теряют введённое, предлагают войти в новой вкладке;
- кабинет при сбое API показывает «не удалось загрузить», а не вход;
- поиск каталога быстрее на больших объёмах; правки доступности (фокус, контраст тёмной темы,
  ошибки у полей, подтверждения).

Новые службы и таймеры после `sudo bash deploy/autodeploy/install.sh` (повторный запуск после
слияния): ежедневная копия, еженедельная проверка восстановления, почасовая проверка,
уведомления о сбоях.

## 3. После обновления

Команды и ожидаемый результат — `DEPLOY_READINESS.md`, раздел 3. Коротко:

- [ ] `ps` — db, api, web, caddy в состоянии `running healthy`;
- [ ] `/health/ready` отвечает `{"status":"ok"}`;
- [ ] журнал `agregator-deploy` заканчивается строкой «готово: <SHA>, проверка пройдена»;
- [ ] ручная копия и проверка восстановления проходят, уведомление приходит;
- [ ] вход, создание заказа, отклик и закрытие заказа проходят вручную в браузере.

## 4. Откат

- Код: `sudo bash deploy/autodeploy/rollback.sh` — возвращает прошлый развёрнутый SHA из
  сохранённых образов без пересборки (несколько минут); текущий SHA помечается неудачным,
  автообновление его не поставит снова.
  Откат отказывает, ничего не меняя, если на сервере есть незакоммиченные правки, нет
  сохранённого SHA, Docker не отвечает или между версиями есть несовместимая миграция —
  причина и порядок действий в выводе (`deploy/README.md`, «Если обновление не прошло»).
- Миграции этого PR откатывать не нужно: старый код работает с новыми столбцами и индексами.
- Данные: восстановление из копии — только по решению владельца, порядок в
  `deploy/README.md` («Резервные копии»), копия перед миграцией лежит в
  `/var/backups/agregator` с пометкой `pre-migration`.
