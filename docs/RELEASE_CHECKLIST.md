# Выпуск PR #39 (ТЗ #37, #40): пакет для решения владельца

Что делает владелец до выкладки, как выкладывать по шагам, что меняется на сервере, как
отменить обновление и что не проверено. Финальный SHA и ссылки на CI — в последнем отчёте
в PR #39. Секретов в документе нет: значения задаются только в `deploy/.env` на сервере.

**Важно: слияние в `main` = выкладка.** Автообновление ставит любой зелёный коммит `main` в
течение нескольких минут. Чтобы между слиянием и выкладкой было отдельное одобрение, перед
слиянием автообновление ставится на паузу (шаг 2 ниже).

## 1. Настройки владельца (до выкладки)

Каждый пункт — одно действие в интерфейсе или в `deploy/.env`; ни один не требует кода.

1. **Защита `main` (DEV-1, Critical).** GitHub → Settings → Rules → Rulesets → New branch
   ruleset. Цель — ветка по умолчанию; Enforcement — Active; список обхода (Bypass list)
   пустой; правила: Restrict deletions, Block force pushes, Require a pull request before
   merging, Require status checks to pass с четырьмя проверками: «Lint, typecheck, test,
   build», «Docker stack (compose)», «Docker stack behind Caddy (proxy)», «Disaster drills
   (backup, restore, broken release, rollback)». Проверка — команды `gh api` из
   `docs/BRANCH_PROTECTION.md`: четыре проверки, `enforcement=active`, `bypass=0`.
2. **Копии вне сервера.**
   - На своём компьютере: `age-keygen -o key.txt`. Строка `public key: age1…` — в
     `deploy/.env` как `BACKUP_AGE_RECIPIENT`. Файл `key.txt` хранить офлайн: без него копии
     не расшифровать.
   - Хранилище у другого провайдера (S3-совместимое) с версионированием. Ключ для сервера —
     запись и список, без удаления. Настройка `sudo rclone config`, имя — в
     `BACKUP_RCLONE_REMOTE` (например, `s3backup:agregator-backups`). Проверка прав —
     `deploy/README.md`, «Резервные копии».
   - `BACKUP_REQUIRE_OFFSITE=true` — копия без выгрузки считается сбоем.
3. **Уведомления и внешний монитор.**
   - Бот Telegram (`NOTIFY_TELEGRAM_TOKEN`, `NOTIFY_TELEGRAM_CHAT`) и/или вебхук
     (`NOTIFY_WEBHOOK_URL`).
   - Внешний монитор (healthchecks.io или аналог) с периодом 1 ч и допуском 1 ч. Его адрес —
     в `MONITOR_HEARTBEAT_URL`: почасовая проверка пингует его или `<адрес>/fail`.
4. **Цели восстановления (решение).** Предложение: закрытый тест — RPO 24 ч, RTO 4 ч;
   публичный запуск — RPO ≤ 1 ч, RTO ≤ 2 ч (ежечасные копии или WAL — отдельная задача);
   откат кода ≤ 15 мин.

## 2. Поэтапная выкладка

Каждый шаг, который меняет сервер, — только с отдельного разрешения владельца. Если
результат шага отличается от ожидаемого, следующий шаг не выполняется.

| Шаг | Кто | Команда / действие | Ожидаемо | Меняет сервер |
|---|---|---|---|---|
| 1. Отчёт о сервере | владелец | `sudo bash deploy/autodeploy/inventory.sh > report.txt` | версия, контейнеры `healthy`, место ≥ 5 ГБ, миграции, журнал; отчёт без секретов | нет |
| 2. Пауза автообновления | владелец | `sudo systemctl stop agregator-deploy.timer` | `systemctl is-active agregator-deploy.timer` → `inactive` | да (обратимо) |
| 3. Копия до выкладки (обязательно) | владелец | под root (`sudo -i`): `mkdir -p -m 700 /var/backups/agregator && cd /opt/agregator && docker compose -f deploy/docker-compose.yml -f deploy/docker-compose.proxy.yml exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=custom' > /var/backups/agregator/before-pr39.dump` | файл не пустой, `head -c 5` → `PGDMP` | только файл копии |
| 4. Решение о слиянии | владелец | merge PR #39 («вливай»), когда CI зелёный на финальном SHA | — | нет (таймер на паузе) |
| 5. Выкладка | владелец | `sudo systemctl start agregator-deploy.service`, затем `journalctl -u agregator-deploy -n 40 --no-pager` | «готово: <SHA>, проверка пройдена» | да |
| 6. Проверки | владелец | раздел 4 ниже | все пункты | нет |
| 7. Копия и восстановление новыми скриптами | владелец | `cd /opt/agregator && sudo bash deploy/backup/backup.sh manual && sudo bash deploy/backup/restore-check.sh` | `mode=offsite-hash-checked` (или `offsite-size-checked`) в `/var/lib/agregator-deploy/backup-status`, `result=ok`, число пользователей как в базе | только файлы копии |
| 8. Наблюдение | владелец | несколько раз за сутки `sudo bash deploy/autodeploy/monitor.sh`; уведомления, внешний монитор | без тревог, пинги монитора идут | нет |
| 9. Таймеры и автообновление | владелец | `sudo bash deploy/autodeploy/install.sh` — включает таймеры копии, проверки восстановления, почасовой проверки и снова автообновление | `systemctl list-timers 'agregator-*'` — все таймеры; предупреждений о мониторе, хранилище и уведомлениях нет, если раздел 1 сделан | да |

Почему шаг 3 обязателен: выкладку выполняет автообновление, которое уже стоит на сервере
(версия из `main` до этого PR). Оно ещё не делает копию перед миграцией — это появляется
только с этим PR. Новые таймеры заработают после шага 9; до него проверки запускаются вручную.

Если на шагах 5–8 что-то не так — раздел 5.

## 3. Что меняется на сервере

Миграции применяются при выкладке автоматически (копия до них — шаг 3; со следующих
обновлений копию перед миграцией делает новое автообновление). Совместимость с прежним API проверена в CI (`schema-compat-test.sh`: прежний API на
новой схеме и на данных прежнего формата) и проверкой миграций (`migration-check.sh`).

| Миграция | Что делает | Прежний код на новой схеме |
|---|---|---|
| `20261019090000_external_accounts` | таблица привязок банков (уже в `main`, PR #38) | — |
| `20261019100000_job_request_id_bid_job_changed` | `jobs.request_id` (+ уникальный индекс), `bids.job_changed_at` | столбцы с NULL; индекс помечен rollback-safe: прежний код пишет NULL |
| `20261019110000_job_close_outcome_bid_reject_reason` | два enum, `jobs.close_outcome`, `bids.reject_reason`, заполнение причины у отклонённых откликов | столбцы с NULL |
| `20261019120000_catalog_search_indexes` | `pg_trgm`, три GIN-индекса, частичный индекс, удаление неиспользуемого индекса | только индексы; удаление помечено rollback-safe |
| `20261019130000_job_request_hash` | `jobs.request_hash` | столбец с NULL |

**Простой.** Образы собираются, пока работает прежняя версия. Затем migrate применяет
миграции (на текущем объёме — секунды, индексы строятся без `CONCURRENTLY` и на это время
блокируют запись в `jobs`), после чего пересоздаются api и web. В CI api становится healthy
примерно через 5 с, web — ещё через 5 с. Ожидаемо: от 10 до 30 секунд ответов 502 через
Caddy. Это не выкладка без простоя; лучше выкладывать, когда тестировщики не работают.

Новое поведение для тестировщиков:
- **Публикация:** повторная отправка не создаёт второй заказ; при другом содержимом —
  понятный отказ.
- **Две вкладки:** правка заказа и черновик не затирают друг друга, а предупреждают.
- **Отклики:** пометка «заказ изменён после вашего отклика»; у отклонённых — причина.
- **Закрытие заказа:** с исходом.
- **Истёкшая сессия:** не теряет введённое.
- **Сбой API:** кабинет показывает «не удалось загрузить», а не страницу входа.
- **Прочее:** поиск быстрее; правки доступности.

## 4. Проверки после выкладки

Команды — `DEPLOY_READINESS.md`, раздел 3.

- [ ] `ps`: db, api, web, caddy — `running healthy`, migrate завершён.
- [ ] `/health/ready` отвечает `{"status":"ok"}`; главная по HTTPS — 200; закрытые разделы
      без входа тестировщика — 401.
- [ ] API: вход, список заказов, создание заказа, отклик, выбор исполнителя, закрытие — вручную
      в браузере под тестовыми аккаунтами.
- [ ] Журнал `agregator-deploy` заканчивается «готово: <SHA>, проверка пройдена»; в `history`
      — новый SHA.
- [ ] Пришло тестовое уведомление (`sudo bash deploy/autodeploy/notify.sh "проверка"`), во
      внешнем мониторе есть пинг.

## 5. Как отменить обновление

- **Код (несколько минут, без пересборки):**
  - Команда: `sudo bash deploy/autodeploy/rollback.sh` — вернёт предыдущую развёрнутую версию
    из сохранённых образов; текущая помечается неудачной, автообновление её не вернёт.
  - Миграции этого PR откат не блокируют: все операции либо безопасны для прежнего кода, либо
    помечены с обоснованием.
  - Откат отказывает и ничего не меняет, если на сервере есть изменения или посторонние файлы,
    нет сохранённого SHA, Docker или база не отвечают, или в базе применена опасная миграция.
    Причина и порядок действий — в выводе.
  - Если не удалось переключить контейнеры, код возвращается на текущую версию, состояние не
    меняется, приходит уведомление.
- **Данные — только по решению владельца:**
  - Копии: перед миграцией (`*-pre-migration.dump`) и до выкладки (`before-pr39.dump`).
  - Порядок: остановить api и web, `pg_restore --clean` из копии, затем `rollback.sh`.
    Подробнее — `deploy/README.md`, «Резервные копии».
  - Данные, записанные после копии, потеряются.
- **Автообновление на паузе:** `sudo systemctl stop agregator-deploy.timer` — пока
  разбираетесь, сервер не поставит следующий коммит.

## 6. Что не проверено

- **Реальный VPS.** systemd-таймеры, объём базы и время восстановления на нём, хранилище и бот
  владельца, права ключа хранилища у конкретного провайдера. Всё перечисленное проверено
  только в CI на одноразовом стеке и заглушками.
- **Safari.** На настоящем iPhone не проверялся: только WebKit в CI (эмуляция iPhone 13).
- **Web vitals на production не замерялись.** Числа в `PERFORMANCE_REPORT.md` — localhost.
- **Видео на главной.** Около 18 МБ за первые 5 секунд на компьютере. Решение о весе —
  `PERFORMANCE_REPORT.md` §4.
- **Внешнего пентеста не было.** Утверждения «система безопасна» нет.
- **Проверки — ограждения, а не доказательство.** Проверка миграций — статический анализ
  SQL; совместимость с прежним API доказывает только исполняемый сценарий
  `schema-compat-test.sh` для этого набора миграций. Проверка секретов в образах ищет файлы и
  имена переменных, а не значения.
