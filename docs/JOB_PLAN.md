# План работ и этапы заказа (фаза 2, сделка без денег)

Первый PR фазы 2 из `ROADMAP.md`: переходы состояний проверены тестами, доступ — только у
сторон сделки. Деньги не затрагиваются: ни оплаты, ни удержания, ни сумм к выплате (гейт
фазы 3). Типы и правила — `packages/shared/src/plans.ts`, API — `apps/api/src/plans`.

## Решения владельца

| Вопрос | Решение |
|---|---|
| Кто составляет план | Гибко: исполнитель (по умолчанию) или заказчик. Выбирает заказчик, пока план не отправлен на согласование. Согласует другая сторона |
| Порядок этапов | Гибко: настройка плана «строго по порядку» или «в любом порядке»; входит в согласуемый план |
| Ограничение доработок | Нет |
| Контакты сторон после выбора | Не показываются; общение — через сервис (чат — следующий PR) |
| Отказ исполнителя после выбора | Да, с причиной: заказ снова открыт, отклики, отклонённые из-за его выбора, снова на рассмотрении |
| Хранение фото (PR чата и фото) | Закрытый тест — в базе (попадают в копии и проверку восстановления); перед публичным запуском — S3-совместимое хранилище российского провайдера: `docs/JOB_CHAT.md` |
| Письма пользователям | Отложено |

## Сценарий

1. Заказчик выбирает исполнителя (как раньше) — заказ «в работе», плана нет.
2. Составитель собирает план: от 1 до 10 этапов (название, что входит, срок в днях — по
   желанию) и порядок сдачи. Черновик сохраняется, затем отправляется на согласование.
3. Другая сторона согласует план или возвращает с комментарием; возвращённый план снова
   правится составителем.
4. Исполнитель сдаёт этапы с комментарием (по порядку — только следующий после принятого).
5. Заказчик принимает этап или возвращает на доработку с комментарием; доработанный этап
   сдаётся снова.
6. Все этапы приняты — заказчику предлагается закрыть заказ как выполненный (действующее
   закрытие с исходом).
7. В любой момент работы исполнитель может отказаться от заказа с причиной.

## Состояния

| Переход | Кто | Условия |
|---|---|---|
| Сохранить черновик | составитель | план DRAFT, версия совпадает |
| Сменить составителя | заказчик | план DRAFT, версия совпадает |
| DRAFT → PROPOSED | составитель | хотя бы один этап, версия совпадает |
| PROPOSED → APPROVED | другая сторона | версия совпадает |
| PROPOSED → DRAFT | другая сторона | причина 5–1000 символов |
| Этап → SUBMITTED | исполнитель | план APPROVED; этап PLANNED или REWORK; по порядку — все предыдущие ACCEPTED |
| SUBMITTED → ACCEPTED | заказчик | — |
| SUBMITTED → REWORK | заказчик | комментарий 5–1000 символов |
| Отказ исполнителя | исполнитель | заказ в работе |

Все изменения — заказ в работе, транзакция под блокировкой строки заказа (`FOR UPDATE`),
запись в журнал. Повтор того же перехода возвращает текущее состояние (двойной клик, обрыв
связи); переход из другого состояния — 409; чужим — 404; не своей стороне — 403.

## Данные

`job_plans` (один на заказ: составитель, порядок, статус, версия, причина возврата, даты) и
`job_stages` (позиция, название, описание, срок, статус, комментарии сдачи и доработки, даты);
ограничения длины и диапазонов — CHECK в миграции `20261020100000_job_plans_stages`. Внешний
ключ на `jobs` — `ON DELETE CASCADE`. Девять новых значений журнала помечены `rollback-safe`:
API журнал только пишет и не читает. Прежний API на новой схеме проверяет
`scripts/schema-compat-test.sh`.
