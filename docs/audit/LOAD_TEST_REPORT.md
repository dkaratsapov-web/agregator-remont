# Нагрузочный замер

Дата: 23.10.2026. Ответ на P1 аудита («нагрузочный benchmark DB/каталога: p95/p99, explain,
capacity»). Это **локальный замер**, не production: он показывает, где узкие места и какой запас
у одного экземпляра, но не обещает скорость на сервере владельца. Замер на сервере — решение
владельца (`OWNER_VPS_CHECKLIST.md`, п. 19).

## Как мерили

- **Машина:** контейнер разработки, 4 ядра, 15 ГБ памяти. API, сайт, PostgreSQL 16 и
  генератор нагрузки — на одной машине, генератор сам забирает часть процессора.
- **Сборка:** production (`node apps/api/dist/main.js`, `next start`), `NODE_ENV=production`,
  пул Prisma по умолчанию (9 соединений), кэш оценки цены по умолчанию (600 с).
- **Данные** (`scripts/perf/load-seed.sql`): 300 заказчиков с сеансами, 3000 мастеров,
  10 000 или 100 000 заказов (30 % открытых, 50 вариантов города), 15 000 или 150 000 откликов,
  6000 уведомлений. База на 100 000 заказов — 141 МБ. Фото в замер не входили.
- **Нагрузка** (`scripts/perf/load-test.mjs`, без зависимостей): N виртуальных пользователей,
  каждый шлёт следующий запрос сразу после ответа, без пауз. **N пользователей здесь — это
  N запросов одновременно**, что намного тяжелее N живых людей: человек делает паузы в секунды
  между действиями. Каждый виртуальный пользователь — со своим адресом, лимиты запросов подняты
  до 100 000 в минуту на адрес, чтобы мерить приложение, а не лимит.
- **Смесь запросов к API:** каталог 30 %, каталог с поиском, городом и фильтрами 10 %, карточка
  заказа 15 %, `/v1/me` 10 %, сводка и список уведомлений 15 %, свои заказы 5 %, оценка цены 5 %,
  черновик (создать и удалить) 10 %. **Страницы сайта:** каталог 40 %, каталог с поиском 20 %,
  карточка заказа 20 %, кабинет 10 %, главная 10 %.
- По 30 секунд на уровень; CPU — прирост времени процессора по `/proc` каждые 2 с, в процентах
  одного ядра (400 % — все четыре ядра).

Повторить: `psql "$LOAD_DATABASE_URL" -v jobs=100000 -f scripts/perf/load-seed.sql`, запустить
API (порт 4100) и сайт (3100) на этой базе, затем
`node scripts/perf/load-test.mjs --target api --users 10,50,100,300 --seconds 30 --jobs 100000`.

## Выводы

1. **Ошибок нет ни на одном уровне.** При 300 одновременных запросах ни один не упал и не
   получил 5xx: лишние запросы ждут в очереди, время ответа растёт.
2. **Узкое место сайта — рендер страниц.** Один процесс `next start` отдаёт 65–80 страниц в
   секунду (около 100–140 мс процессора на страницу). Дальше растёт только очередь: при 300
   одновременных запросах p95 — 5–7 с. Оценка ёмкости: если живой человек открывает страницу
   раз в 10 с, один процесс сайта выдерживает порядка 650–800 человек одновременно на этой
   машине. Это оценка из замера, а не измерение с людьми.
3. **Узкое место API на 100 000 заказов — подсчёт для страниц каталога.** Каталог отдаёт
   страницу по индексу за 0,2 мс, но число «всего найдено» (`count(*)`) на 100 000 строк — полный
   проход таблицы, около 39 мс (`EXPLAIN ANALYZE`, 23.10.2026). Поэтому Postgres загружен на
   250 %, а пропускная способность API падает с ~720 до ~340 запросов/с.
   **Рекомендация** (не сделано в этом PR, не нужно для беты): хранить число для каталога без
   фильтров в кэше на несколько секунд или показывать «больше N» вместо точного числа.
   На объёмах закрытой беты (сотни заказов) это незаметно.
4. **Соединения с базой.** Пул Prisma — 9 соединений на процесс, в замере не больше 11, очереди
   за соединением не видно: API упирается в процессор раньше.
5. **Память.** API 255–325 МБ, сайт 570–1100 МБ при 300 одновременных запросах. На сервере с
   2 ГБ памяти сайт под пиковой нагрузкой займёт половину — это стоит учесть при выборе сервера.

## Что не мерили

- Production-сервер, настоящую сеть, Caddy с HTTPS — только localhost.
- Загрузку фото и их выдачу (фото хранятся в базе; восстановление копии растёт с их объёмом).
- Длительную нагрузку (часы), утечки памяти, восстановление после перегрузки.
- Время отката и восстановления из копии под нагрузкой.
- Несколько экземпляров API и сайта (лимиты запросов в памяти рассчитаны на один экземпляр).
