# ТЗ: подготовка Agregator Remont к будущим мобильным приложениям (Mobile-ready architecture)

**Статус:** техническое задание для Claude Code; не означает заказ на создание iOS/Android-приложений сейчас.  
**Приоритет:** ближайший отдельный этап архитектурной подготовки после согласования владельцем; небольшие PR.  
**Продукт:** маркетплейс ремонта, первоначальный запуск Москва и Санкт-Петербург.  
**Разделение ролей:** Claude Code реализует; ChatGPT проводит независимое ревью; владелец утверждает merge и релизы.

## 1. Цель и границы
Создать техническую основу, при которой будущие приложения iOS/Android (предпочтительно React Native + Expo после отдельного решения) используют тот же NestJS API, PostgreSQL и бизнес-правила, что и сайт Next.js/PWA. **Сейчас не писать мобильные приложения**, не переносить существующий web UI, не выполнять бессмысленный рефакторинг работающих модулей.

Сохранять все действующие функции сайта, CI, текущие гарантии владения ресурсами, RBAC, журнал изменений, лимиты и блокировки конкурентных операций. Никаких настоящих платежей.

## 2. Аудит готовности — первый deliverable
До реализации составить `docs/MOBILE_READINESS_AUDIT.md`:
- карта текущего API и его потребителей (Next.js Server Actions/RSC); какие функции уже независимы от Web;
- список бизнес-правил, случайно размещённых только в web (отдельно UI-валидация и серверная авторизация);
- инвентаризация DTO/типов `packages/shared`, схем Prisma, ошибок API, пагинации и контрактов;
- модель существующей сессии: web `__Host-ar_session` HttpOnly-cookie → API Bearer; как мобильный клиент сможет безопасно работать без копирования этой cookie-архитектуры;
- карта будущих модулей «контакты/чат/файлы/push/сделки» и межплатформенных границ;
- риски, план миграций без нарушения совместимости, приоритеты P0/P1/P2, оценка трудозатрат;
- явно отметить уже существующие компоненты и не обещать реализованными будущие возможности.

## 3. API-first — обязательные требования
1. **Единый источник бизнес-правил — NestJS service/database**, не Next Server Actions. Проверки ownership, RBAC, статусов заказов/откликов, квот и инвариантов — на API и в БД независимо от клиента.
2. Стабильный версионируемый API (`/v1` уже существует). Определить правила совместимых/несовместимых изменений и депрекации; сохранить существующие контракты или документировать изменение.
3. Добавить генерацию актуальной спецификации **OpenAPI** из API с покрытием auth, jobs, profiles, bids, ошибок, 401/403/404/409/429. Спецификация — часть CI (детерминированная генерация + drift check); не публиковать приватную Swagger UI наружу без защиты. Схемы должны соответствовать реальным DTO и ответам, секреты не включать.
4. Общий типизированный клиент/контракты: оценить `packages/shared`; выбрать минимальный подход к генерации типов OpenAPI для web и будущего React Native. Не создавать второй источник истины. Не переносить `server-only`/Next.js зависимости в общий пакет.
5. Унифицированные JSON ошибки: machine-readable `code` и `message` (+ `fieldErrors` при валидации, если обосновано), стабильные HTTP статусы; не раскрывать внутренние ошибки, email/токены/детали БД. Действующий web не ломать; мигрировать постепенно с тестами.
6. Пагинация, сортировка, фильтры: предсказуемый контракт, лимиты, стабильная сортировка; не выдавать приватные данные в общих списках.
7. CORS — не считать защитой API, браузерный web и будущий native mobile — разные клиенты.

## 4. Авторизация и сессии — отдельный security design
**Не переводить сайт на хранение токенов в localStorage.**
- Сохранить текущую безопасную web схему: HttpOnly Secure SameSite cookie на Next.js, server-side Bearer к API.
- Подготовить `docs/MOBILE_AUTH_DESIGN.md`: рекомендуемая схема native-клиента (системное secure storage: iOS Keychain, Android Keystore; короткоживущий access token и rotation/revocation refresh при необходимости). Конкретную модель утвердить до кодирования.
- Threat model: компрометация устройства, утечка/повтор refresh, replay, logout одного/всех устройств, блокировка после смены пароля, потеря устройства, смена роли, украденный токен, лимиты/abuse.
- Спроектировать серверное управление устройствами/сессиями, безопасный revoke, TTL, hash-only хранение токенов, атомарную ротацию refresh с детектированием повторного использования; не выводить секреты в логах/аналитике.
- Не внедрять новые mobile auth endpoints без отдельного PR, тестов и независимого security review. Существующий auth release gate (`docs/SECURITY.md`) продолжает действовать.

## 5. Web и будущий mobile — разделение ответственности
- Web Server Actions остаются BFF/адаптером, но не самостоятельным источником бизнес-правил.
- Не дублировать предметную логику в разных клиентах; формы могут иметь UX-валидацию, а API — окончательную.
- Будущие React Native/Expo компоненты создаются в отдельном `apps/mobile` только **после** решения владельца; сейчас папку/шаблон не создавать без ясной технической пользы.
- Предусмотреть, чтобы будущие deeplinks открывали заказ/отклик/чат после безопасного подтверждения авторизации и владения. Описать namespace ссылок, не внедрять раннюю сложную маршрутизацию.
- Доступность и удобный мобильный сайт/PWA остаются приоритетом для Москвы/СПб.

## 6. Подготовка коммуникаций, файлов и уведомлений (проектирование)
Составить интерфейсы и схемы, **не реализуя преждевременно**:
- **Сообщения/чат:** идентификаторы диалога и участников, server-side membership, read receipts, пагинация, idempotency отправки, защита от чтения чужого диалога; WebSocket или polling выбрать по реальным потребностям.
- **Файлы/фото:** S3-compatible storage, временные upload/download URLs, проверка доступа на сервере, лимиты/квоты, MIME по сигнатуре, антивирус при необходимости, приватный доступ по умолчанию, запрет SVG/HTML, удаление и retention.
- **Уведомления:** общий event-driven интерфейс + каналы web/email/mobile push; FCM/APNs не внедрять сейчас, предусмотреть registration/revocation device token с владельцем; защититься от повторных уведомлений, утечки содержимого на lock screen и спама.
- **Сделки и платежи:** FSM на API и audit log; платежи/escrow только через отдельного провайдера, sandbox, юридический/security gate — не писать реальную денежную логику в рамках этого ТЗ.

## 7. Безопасность, эксплуатация, совместимость
- Сохранять `SessionGuard`/`RolesGuard`, точечные проверки ownership; тесты «пользователь А не может читать/изменять ресурсы Б» для каждого нового endpoint.
- Серверная валидация + whitelist/forbidNonWhitelisted, запрет mass assignment; идемпотентность операций где уместно.
- Не ослаблять защиту CSRF на Server Actions, `WEB_PUBLIC_ORIGIN`, trust proxy/IP лимиты, HTTPS и изоляцию контейнеров.
- Если потребуется отдельная mobile-facing auth инфраструктура, применять отдельные rate limits, audit и миграции, не нарушая web сессии.
- Ограничение текущего closed-beta vs public launch зафиксировать; все release gates `docs/SECURITY.md` остаются обязательными.
- Документировать observability без ПДн, backup/restore, versioning, reverse compatibility для нескольких версий приложений в магазинах.

## 8. План реализации: небольшие PR
**PR A — архитектурный аудит и дизайн:** `MOBILE_READINESS_AUDIT.md`, `MOBILE_AUTH_DESIGN.md`, API contract/version policy и план работ. **Без изменения runtime-кода.** Показать владельцу ключевые архитектурные решения, требующие согласования.

**PR B — OpenAPI и контроль контракта:** спецификация, генератор/типизация, проверка в CI, тесты `auth/jobs/bids/profiles`, README; не менять поведение API без веской причины.

**PR C — унификация ошибок и shared API client (при необходимости):** минимальные совместимые изменения, тесты всех сценариев, без потери работы существующего Next.js.

**PR D — подготовка интерфейсов коммуникаций/файлов/уведомлений:** по умолчанию только ADR/контракты и backlog; реализацию производить вместе с соответствующей Фазой 2, без мёртвых абстракций.

После каждого PR — независимый аудит ChatGPT, исправления в той же ветке, merge только после явного одобрения владельца. **Начать с PR A**, не смешивать все этапы в один большой PR.

## 9. Критерии приёмки
- Документирована схема единого API для сайта, iOS и Android, без обязательной переработки backend ради native приложения.
- Ясно обозначены неизменные функции и будущие изменения; перечислены риски auth, API и BFF.
- На стадии PR B OpenAPI воспроизводим, отражает реальные DTO, CI проверяет drift, договорённости по ошибкам и версиям сохранены.
- Ни одна защищённая операция не зависит от доверия к данным веб-клиента; тесты 401/403/404/409/429 и отсутствие утечек ПДн.
- Текущие API endpoints и страницы web продолжают работать, smoke/integration/CI green, никаких реальных платежей.
- Документация, миграции (если возникнут), rollback strategy, риски и оставшиеся release gates описаны в каждом PR.
