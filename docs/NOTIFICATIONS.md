# Уведомления в кабинете (фаза 2)

Третий PR фазы 2 после плана и этапов (`docs/JOB_PLAN.md`) и переписки (`docs/JOB_CHAT.md`).
Типы — `packages/shared/src/notifications.ts`, API — `apps/api/src/notifications`, тексты —
`apps/web/src/lib/notifications.ts`. Почта и пуш отложены владельцем.

## Что видит человек

- **Колокольчик в шапке** с числом непрочитанных (99+ для больших чисел). Число приходит со
  страницей и обновляется раз в минуту, пока вкладка на экране, и сразу при возврате на вкладку.
- **Страница «Уведомления»** (`/account/notifications`): новые сверху, по 30 на странице
  («Ранние» — дальше). Непрочитанные — с терракотовой меткой. Строка — обычная ссылка: на заказ
  (заказчику), на «Ход работ» (исполнителю), сразу к откликам, плану или переписке. Кнопка
  «Отметить все прочитанными».
- **Пометка «Новое»** у заказов в «Моих заказах» и «Моих откликах», пункт в меню кабинета и на
  главной кабинета.
- **Прочтение при открытии заказа**: уведомления заказа становятся прочитанными, когда открыта
  его страница (заказчика, «Ход работ» или карточка в каталоге — туда ведёт отклонённый отклик).
  Если сообщение пришло, пока страница открыта, оно тоже сразу прочитано.
- Без JavaScript: список и ссылки работают, «Отметить все прочитанными» — обычная форма;
  прочтение при открытии заказа и обновление числа — только с JS.

## События

| Событие | Кому | Текст |
|---|---|---|
| Новый отклик | заказчику | «Новый отклик» + цена и срок |
| Отклик отозван | заказчику | «Мастер отозвал отклик» |
| Исполнитель выбран | ему | «Вас выбрали исполнителем» |
| Выбран другой / заказ закрыт без выбора | остальным откликнувшимся | с причиной |
| План прислан / согласован / возвращён | другой стороне сделки | |
| Сменился составитель плана | исполнителю | |
| Этап сдан | заказчику | «Этап сдан, проверьте работу» + этап |
| Этап принят / на доработку | исполнителю | + этап |
| Исполнитель отказался | заказчику | заказ снова открыт |
| Заказ закрыт | исполнителю сделки | «завершён» или «отменён» |
| Новые сообщения | другой стороне | собираются в одно: «3 новых сообщения» |

Тот, кто действовал, уведомления не получает. Повтор того же действия (двойной клик, обрыв
связи) второго уведомления не создаёт: повторы в API возвращаются раньше записи.

## Как устроено

- Таблица `notifications`: получатель, заказ, вид, счётчик (для сообщений), снимок подробностей
  (`data`: цена, срок, название этапа, причина, исход — этап может быть удалён вместе с планом),
  время прочтения. Название заказа берётся текущее.
- Пишется **в той же транзакции, что и событие** (`notify`, `notifyMessage` в
  `apps/api/src/notifications/notify.ts`): нет события без уведомления и наоборот.
- Непрочитанные новые сообщения по заказу — **одна строка со счётчиком**: частичный уникальный
  индекс `notifications_message_unread_key` и `INSERT … ON CONFLICT`, поэтому и параллельные
  сообщения дают одну строку. Прочитанная строка остаётся в истории, следующее сообщение
  начинает новую.
- Отзыв отклика теперь берёт строку заказа (`FOR KEY SHARE`) до строки отклика: внешний ключ
  уведомления на заказ иначе замыкал цикл блокировок с выбором исполнителя (найдено тестом
  гонок `bids-concurrency`).
- API: `GET /v1/me/notifications?cursor=`, `GET /v1/me/notifications/summary` (всего и по
  заказам), `POST /v1/me/notifications/read` с ровно одним из `all`, `jobId`, `ids` (до 100).
  Только свои: чужие id и заказы молча не находятся, чужой курсор — 400.
- Сводка на странице берётся один раз за рендер (`getUnreadSummary`, React `cache`): шапка,
  списки и страница заказа используют один запрос.

## Данные и миграция

Миграция `20261022100000_notifications` — новые тип и таблица, внешние ключи
`ON DELETE CASCADE` (уведомления уходят с заказом и пользователем), CHECK на счётчик (1–10000)
и `data` (объект до 1 КБ). Прежний API на новой схеме работает и уведомлений не пишет
(`scripts/schema-compat-test.sh`). Текст сообщений и контакты в уведомления не копируются.

## Проверки

- API e2e `notifications.e2e-spec.ts` (12): все события и получатели, повторы без дублей,
  счётчик сообщений (в том числе параллельных), прочтение по заказу/списку/всем, чужие
  уведомления, неверные запросы, курсор, удаление с заказом, ограничения базы.
- Сверка контракта по новым операциям и кодам ответа (`contract.e2e-spec.ts`).
- Web: тексты всех видов и ссылки (`notifications.test.ts`), Server Actions прочтения.
- Браузер `notifications-e2e.mjs` двумя пользователями: колокольчик, «Новое» в списках, переход
  из списка и прочтение, сообщение при открытой странице, «Отметить все», без JS, 320 px.

## Решения по своим жалобам

В число на колокольчике входят и непросмотренные решения по своим жалобам
(`NotificationsSummaryDto.reportDecisions`); они хранятся не в таблице уведомлений, а отметкой
`reports.reporter_seen_at`: новые виды уведомлений не добавлялись, потому что прежний API при
откате не прочитал бы неизвестное значение enum. Страница уведомлений ссылается на «Мои жалобы»;
«Отметить все прочитанными» отмечает и решения.

## Не входит

- Почта и пуш-уведомления (отложено владельцем).
- Настройки «что присылать» — появятся вместе с почтой.
- Автоудаление старых уведомлений — при росте объёма (сейчас удаляются с заказом).
