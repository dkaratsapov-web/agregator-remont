# Переписка по заказу и фото-отчёты (фаза 2, без денег)

Второй PR фазы 2 после плана и этапов (`docs/JOB_PLAN.md`). Типы и лимиты —
`packages/shared/src/messages.ts`, API — `apps/api/src/messages` и `apps/api/src/photos`.

## Что умеет

- **Переписка** между заказчиком и выбранным исполнителем: блок «Переписка» на странице заказа
  и на странице «Ход работ». Текст до 2000 символов и/или до 5 фото. Новые сообщения
  подгружаются раз в 20 с, пока вкладка открыта. Без JS всё работает, обновление — вручную.
- **Своя переписка для каждой сделки**: если исполнитель отказался и выбран другой, новый
  исполнитель прежнюю переписку не видит; заказчик видит переписку с текущим исполнителем.
- Писать можно, пока заказ в работе; после закрытия переписка остаётся **только для чтения**.
- **Фото-отчёт к сдаче этапа**: к комментарию «Этап сдан» можно приложить до 5 фото; заказчик
  видит их у этапа. Повтор той же сдачи фото не добавляет. Отказ исполнителя удаляет план, а
  с ним этапы и их фото (переписка остаётся в базе).
- Контакты сторон по-прежнему не показываются — договариваются в переписке.

## Доступ

Переписку и фото видят только заказчик-владелец и исполнитель этой сделки; фото — ещё
администратор (разбор спора). Остальным — 404, как будто заказа нет. Фото отдаёт кабинет
(`/account/photos/<заказ>/<фото>`) по сессии; в браузере кешируется только для этого
пользователя и не дольше суток.

## Фото

- Принимаются JPG, PNG, WebP; формат определяется по содержимому, а не по расширению.
- До 5 файлов за раз, каждый до 8 МБ, весь запрос до 26 МБ (Caddy пропускает такие тела
  только на страницах заказа и «Хода работ», остальное — до 8 МБ).
- С JavaScript браузер сразу после выбора уменьшает фото до 2000 px (JPEG): снимок телефона
  4–8 МБ уходит примерно за 0,5–1 МБ.
- API перекодирует каждое фото (sharp): поворот по EXIF, WebP без метаданных — **геолокация и
  сведения о телефоне не сохраняются**; полное фото до 2000 px и миниатюра до 480 px.

## Где хранятся фото и почему

Решение для закрытого теста: **в базе** (таблица `job_photo_blobs`, байты отдельно от списков).
Так фото автоматически попадают в ежедневную копию, шифрованную копию вне сервера и проверку
восстановления — без нового провайдера, ключей и настроек. Одно фото после перекодирования —
примерно 0,2–0,5 МБ; при сотнях фото на закрытом тесте база растёт на десятки–сотни МБ.

Перед публичным запуском — перенести в S3-совместимое хранилище российского провайдера
(закрытый бакет, временные ссылки): меняются только `PhotosService.attach` и `read`, схема
сообщений и интерфейс остаются. Нужен выбор провайдера и ключей — решение владельца.

## Данные

`job_messages` (заказ, исполнитель сделки, автор, текст, ключ отправки), `job_photos` (заказ,
исполнитель сделки, кто загрузил, ровно одно из: сообщение или этап — CHECK; размеры),
`job_photo_blobs` (полное фото и миниатюра). Миграция `20261021100000_job_messages_photos` —
только новые таблицы, внешние ключи `ON DELETE CASCADE`: прежний API работает на новой схеме
(`scripts/schema-compat-test.sh`). Повтор отправки той же формы (двойной клик, обрыв связи)
не создаёт копию: у формы свой ключ (`request_id`, уникален для автора).

## Проверки

- API e2e `messages.e2e-spec.ts` (11): доступ, обе стороны пишут, пустое и длинное сообщение,
  повтор с ключом, закрытый заказ, новый исполнитель после отказа, перекодирование фото (поворот,
  без EXIF, миниатюра), посторонние и администратор, неверные файлы и лимиты, фото-отчёт к этапу.
- Сверка контракта по всем новым операциям и кодам ответа (`contract.e2e-spec.ts`).
- Web: Server Actions сообщения и сдачи с фото (unit), разбор фото из формы.
- Браузер `chat-e2e.mjs` двумя пользователями: автообновление, уменьшение фото в браузере,
  миниатюра и полное фото, фото-отчёт к этапу, сообщение без JS, посторонний получает 404,
  320 px без горизонтальной прокрутки, закрытый заказ — только чтение.
- Лимиты Caddy проверены на настоящем Caddy с сервером, который дочитывает тело: 9 МБ — 413
  на обычной странице и проходит на странице заказа; 28 МБ — 413. В CI это не проверяется:
  Caddy отвечает 413, только когда приложение читает тело, а Next.js на обычную страницу
  отвечает раньше — проверка через curl зависела бы от Next.js, а не от Caddy.

## Не входит

- Уведомления о новых сообщениях (почта отложена владельцем; в кабинете — без счётчика
  непрочитанного).
- Модерация переписки и жалобы.
- Хранение в S3 (см. выше).
