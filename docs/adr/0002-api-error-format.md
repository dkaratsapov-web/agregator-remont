# ADR 0002. Единый формат ошибок API с машинным `code`

**Статус:** Принято владельцем (Issue #10), редакция 2 — после аудита PR #11.
**Реализовано** в PR #47 (раздел «Реализация» в конце).

## Контекст

Сейчас ошибки — стандартный формат NestJS `{ statusCode, message, error }`. `message` —
русская строка, для ошибок валидации DTO — массив строк. Машинного кода нет: пять разных 409
и два разных 429 (лимит частоты и суточная квота) различимы только по тексту.

Заголовки повтора сейчас: `@nestjs/throttler` ставит стандартный `Retry-After` только для
лимита `default`; для именованных лимитов `auth` и `write` — заголовки `Retry-After-auth` и
`Retry-After-write`. Суточные квоты (`HttpException 429` в сервисах) заголовков повтора не
ставят.

## Решение

### 1. Wire-schema (v1, аддитивно к текущему формату)

```ts
interface ApiError {
  statusCode: number;            // совпадает с HTTP-статусом ответа
  code: string;                  // UPPER_SNAKE_CASE, всегда присутствует
  message: string | string[];    // как сейчас: строка; массив только у VALIDATION_FAILED
  error: string;                 // как сейчас: текстовое имя статуса («Conflict»)
  fieldErrors?: FieldError[];    // только у VALIDATION_FAILED
}

interface FieldError {
  path: string;                  // путь к полю: "title", "categories.2", "device.platform"
  code: string;                  // INVALID | REQUIRED | TOO_SHORT | TOO_LONG | OUT_OF_RANGE | UNKNOWN_FIELD
  message: string;               // текст для показа рядом с полем
}
```

Правила `fieldErrors`:
- путь собирается из вложенных ошибок class-validator через точку; индекс массива —
  числом (`categories.2`);
- лишнее поле, отклонённое `forbidNonWhitelisted`, — запись с путём этого поля и
  `code: UNKNOWN_FIELD`;
- ошибки, не относящиеся к одному полю (например, `budgetMin > budgetMax`,
  «Нет полей для изменения»), — **не** в `fieldErrors`, а отдельным `code`
  (`BUDGET_RANGE_INVALID`, `NO_FIELDS_TO_UPDATE`) со строкой в `message`;
- `message` у `VALIDATION_FAILED` остаётся массивом тех же текстов, что в `fieldErrors`
  (совместимость с текущим web).

### 2. Каталог кодов

| HTTP | `code` | Когда | Повтор |
| --- | --- | --- | --- |
| 400 | `VALIDATION_FAILED` | DTO/query не прошли проверку | нет, исправить ввод |
| 400 | `BAD_REQUEST` | некорректный JSON, иное 400 | нет |
| 400 | `NO_FIELDS_TO_UPDATE` | пустой PATCH | нет |
| 400 | `BUDGET_RANGE_INVALID` | `budgetMin > budgetMax` | нет |
| 401 | `UNAUTHENTICATED` | нет или недействительная сессия | нет; войти заново |
| 401 | `INVALID_CREDENTIALS` | неверный email или пароль (одинаково для обоих случаев) | нет |
| 403 | `FORBIDDEN_ROLE` | роль не допускает операцию | нет |
| 404 | `NOT_FOUND` | ресурса нет **или он чужой** — один код, чтобы не раскрывать существование | нет |
| 409 | `EMAIL_TAKEN` | регистрация на занятый email | нет |
| 409 | `JOB_NOT_OPEN` | правка/отклик/выбор исполнителя для неоткрытого заказа | нет |
| 409 | `JOB_ALREADY_CLOSED` | повторное закрытие | нет |
| 409 | `BID_ALREADY_EXISTS` | второй отклик на заказ | нет |
| 409 | `BID_NOT_PENDING` | отзыв или выбор отклика не в статусе «на рассмотрении» | нет |
| 413 | `PAYLOAD_TOO_LARGE` | тело запроса больше лимита | нет |
| 429 | `RATE_LIMITED` | лимит частоты (`default`, `auth`, `write`) | да, не раньше `Retry-After` |
| 429 | `DAILY_QUOTA_EXCEEDED` | суточная квота заказов/откликов | автоматически нет; `Retry-After` — когда квота освободится |
| 500 | `INTERNAL` | всё непредвиденное; текст общий, без деталей | GET — с паузой; POST — только с `Idempotency-Key` |
| 503 | `UNAVAILABLE` | БД или зависимость недоступна | как 500 |

Общие коды по статусу (`BAD_REQUEST`, `FORBIDDEN`, `CONFLICT`) используются только для
ошибок, у которых нет более точного кода; каждый новый доменный случай получает свой код.

### 3. Семантика повтора

- `RATE_LIMITED`: всегда стандартный `Retry-After` в секундах. Глобальный фильтр берёт
  наибольшее из `Retry-After`, `Retry-After-auth`, `Retry-After-write`, выставленных
  throttler'ом, и ставит его как `Retry-After`. Именованные заголовки сохраняются.
- `DAILY_QUOTA_EXCEEDED`: `Retry-After` — секунды до момента, когда самая старая запись в
  скользящем 24-часовом окне выйдет из него. Клиент не повторяет автоматически, а показывает
  пользователю, когда можно снова.
- Сетевые ошибки и 5xx: клиент повторяет только идемпотентные запросы (GET) с
  экспоненциальной паузой; создания — только с `Idempotency-Key` (ADR 0005).

### 4. Запасной вариант для неизвестного кода

Клиент, получивший неизвестный `code`, действует по классу статуса: 4xx — показать
`message`; 401 — экран входа; 429 — подождать `Retry-After`; 5xx — общий текст «Не удалось
выполнить, попробуйте позже». Это требование к первой мобильной сборке (ADR 0001).

### 5. Преобразование исключений (глобальный фильтр, PR C)

| Исключение | Статус | `code` |
| --- | --- | --- |
| Доменная ошибка `ApiError(code, status, message)` из сервисов | её статус | её код |
| `ValidationPipe` (`BadRequestException` с массивом ошибок) | 400 | `VALIDATION_FAILED` + `fieldErrors` |
| `ThrottlerException` | 429, заголовки сохраняются | `RATE_LIMITED` |
| Прочие `HttpException` (встроенные Nest, ошибки разбора тела) | **их собственный статус** | по статусу: 400 `BAD_REQUEST`, 401 `UNAUTHENTICATED`, 403 `FORBIDDEN`, 404 `NOT_FOUND`, 409 `CONFLICT`, 413 `PAYLOAD_TOO_LARGE`, 429 `RATE_LIMITED` |
| Ошибки Prisma и любые другие исключения | 500 (недоступность БД — 503) | `INTERNAL` / `UNAVAILABLE` |

- Фильтр **не меняет статус** известных `HttpException` (400/404/413/429 не превращаются в
  500) и не удаляет заголовки, выставленные до него.
- Ошибки Prisma автоматически в 4xx не преобразуются: ожидаемые ситуации (уникальность,
  «не найдено») сервисы обрабатывают явно, как сейчас (`bids.service` для повторного
  отклика).
- В ответ не попадают стек, SQL, имена таблиц и полей БД, email, токены. В серверный лог —
  код, статус, маршрут, id пользователя, без тела запроса и ПДн.

### 6. Тесты (PR C)

- Каждый код из каталога — хотя бы один e2e со статусом, телом и (для 429) заголовками.
- `fieldErrors`: вложенное поле, индекс массива, лишнее поле, ошибка не по полю.
- Неизвестное исключение → 500 `INTERNAL`, тело без стека и деталей.
- Ошибка разбора JSON → 400, большое тело → 413, несуществующий маршрут → 404 (не 500).
- Ни один ответ об ошибке не содержит email, токенов, хешей (проверка по телам тестов).
- Web: показ ошибок по `code` с запасным вариантом по `message`; существующие тесты web и
  интеграционные сценарии зелёные.

## Последствия

- Совместимо для текущего web (поля не удаляются); мобильные клиенты получают стабильные коды
  и предсказуемый повтор.
- Новый код внутри существующего статуса — совместимое изменение при наличии запасного
  варианта в клиенте (ADR 0001).
- Тексты остаются русскими; при локализации приложения клиент может переводить по `code`.

## Альтернативы

- **RFC 9457 `application/problem+json`** (`type`, `title`, `detail`) — стандартнее, но
  меняет форму ответа и ломает текущий web; можно принять в `/v2`.
- **Только `message` без кода** — текущее состояние, не подходит для native.

## Реализация (PR #47)

- **Где.**
  - Фильтр и проверка ввода — `apps/api/src/common/exception-filter.ts` (`ApiExceptionFilter`,
    `ApiValidationPipe`), подключены в `setup-app.ts`.
  - Доменные ошибки — `apps/api/src/common/api-error.ts` (`ApiError`, `QuotaExceeded`).
  - Типы — `packages/shared/src/errors.ts` (`API_ERROR_CODES`, `ApiErrorBody`, `FieldError`).
  - Схема OpenAPI `ErrorResponse`: `code` и `error` обязательны, сверка типов — в
    `contract-checks.ts`.
- **Доменные коды.** Каталог из раздела 2 введён в местах, где возникают эти ошибки:
  - `EMAIL_TAKEN`, `INVALID_CREDENTIALS`, `FORBIDDEN_ROLE`;
  - `JOB_NOT_OPEN`, `JOB_ALREADY_CLOSED`, `BID_ALREADY_EXISTS`, `BID_NOT_PENDING`;
  - `NO_FIELDS_TO_UPDATE`, `BUDGET_RANGE_INVALID`;
  - `DAILY_QUOTA_EXCEEDED` (заказы, отклики, жалобы, заявки) с `Retry-After` до освобождения
    квоты.

  Остальные конфликты пока получают общий код по статусу (`CONFLICT` и т. п.). Новые доменные
  коды добавляются по мере надобности клиентам — это совместимое изменение.
- **Отличия от текста выше.**
  - `isLength` (одно ограничение на обе границы) даёт `OUT_OF_RANGE`, а не
    `TOO_SHORT`/`TOO_LONG`.
  - Тексты вложенных ошибок стали чистыми. Раньше NestJS приклеивал путь к тексту
    («stages.0.Название этапа…»), теперь путь — в `fieldErrors[].path` (`stages.0.title`), а
    текст — для человека.
  - Ошибки разбора тела (body-parser) сохраняют свой статус: битый JSON — 400 `BAD_REQUEST`,
    слишком большое тело — 413 `PAYLOAD_TOO_LARGE`. Без этого второй случай получал 500.
- **Web.** `ApiError.code` в `apps/web/src/lib/api.ts`; показ по-прежнему по `message`, код
  доступен для точных текстов.
- **Тесты.**
  - `apps/api/test/errors.e2e-spec.ts` — каждый код со статусом и телом, `fieldErrors` (вложенное
    поле, индекс, лишнее поле), `Retry-After` у лимита и квоты, 500/503 без деталей, ни email, ни
    хешей в теле.
  - Контракт всех ответов-ошибок — `contract.e2e-spec.ts`.
