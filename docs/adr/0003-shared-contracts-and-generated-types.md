# ADR 0003. Общие контракты: `packages/shared` и типы из OpenAPI

**Статус:** Предложено (PR A, Issue #10), редакция 2 — после аудита PR #11.
Реализация — PR B (генерация и проверки), PR C (переход на сгенерированные типы).

## Контекст

`packages/shared` содержит две разные вещи:

1. **Константы и правила ввода**: `JOB_CATEGORIES`, `JOB_STATUSES`, `BID_STATUSES`,
   `USER_ROLES`, `JOB_LIMITS`, `BID_LIMITS`, `PROFILE_LIMITS`, `AUTH_LIMITS`, `PAGINATION`,
   русские названия. Их используют и DTO-валидаторы API, и формы web.
2. **Интерфейсы ответов**: `JobDto`, `OwnJobDto`, `UserDto`, `AuthSessionDto`, `BidDto`,
   `MyBidDto`, `JobBidDto`, `ContractorProfileDto`, `Paginated<T>`. Пишутся вручную; API
   возвращает их через явные мапперы.

Пакет не зависит от Next.js и `server-only` и собирается в CommonJS. После PR B появится
OpenAPI — второе описание тех же ответов. Совпадение TypeScript-типов не доказывает, что
реальный JSON на проводе совпадает со схемой (сериализация, `null` vs отсутствие поля,
generic-обёртки вроде `Paginated<T>`).

## Решение

**Основной контракт — `apps/api/openapi.json`, сгенерированный из кода API и проверенный на
реальных ответах.** TypeScript-типы ответов для клиентов генерируются из него. Константы
остаются рукописными в `shared` и являются источником истины для ограничений ввода.

```
packages/shared (константы, лимиты, enum'ы) ──▶ DTO-валидаторы API, формы web/mobile
код API (классы схем ответов) ──▶ openapi.json ──▶ сгенерированные типы (packages/shared/src/generated)
                                     ▲
              e2e: реальные ответы валидируются по openapi.json (ajv, строгий режим)
```

### Три проверки, а не одна

1. **Типы** (`pnpm typecheck`): классы схем ответов в API `implements` интерфейсов `shared`;
   сгенерированные типы и рукописные интерфейсы взаимно присваиваемы. Ловит расхождение
   описаний, но не JSON на проводе.
2. **Drift** (CI): перегенерация `openapi.json` и типов даёт пустой `git diff`.
3. **Wire** (e2e, CI): ответы и ошибки всех маршрутов из ADR 0001 валидируются по схеме из
   `openapi.json` в строгом режиме: `additionalProperties: false` у схем ответов, все
   `required` поля обязаны присутствовать, форматы проверяются. Ловит лишние поля, пропуски,
   `undefined` вместо `null`, неверные типы. Это и есть доказательство, что схема равна
   реальному ответу.

### Правила представления данных (фиксируются в схеме)

| Что | Правило |
| --- | --- |
| Отсутствующее значение | поле **всегда присутствует** со значением `null` (`nullable: true` + `required`); поля не опускаются |
| Необязательные поля в ответах | не используются; в запросах — допустимы (`required` не указан) |
| Числа | целые (`integer`): деньги — целые рубли, сроки — целые дни, `page`/`limit`/`total`; дробных чисел и `decimal` в API нет. Появление дробных сумм (Фаза 3) — строкой в минимальных единицах или целыми копейками, отдельным решением |
| Даты | строка ISO 8601 UTC, `format: date-time` |
| Enum'ы | строковые enum'ы; открытый/закрытый — по ADR 0001 |
| Массивы | всегда присутствуют, пустой массив вместо `null` |
| `Paginated<T>` | отдельная именованная схема на каждый `T` (`PaginatedJobDto`, `PaginatedOwnJobDto`, `PaginatedMyBidDto`), без generic-магии в генераторе |
| Идентификаторы | строки (`cuid`), клиенты не разбирают их структуру |

### Шаги

1. **PR B.** Классы схем ответов с декораторами `@nestjs/swagger`, генерация
   `openapi.json` и типов (`openapi-typescript`, только типы, без runtime), три проверки выше.
2. **PR C.** Рукописные интерфейсы ответов в `shared` удаляются и заменяются псевдонимами
   сгенерированных типов (`export type JobDto = components['schemas']['JobDto']`), имена
   экспортов не меняются, web не переписывается. После PR C **рукописных интерфейсов ответов
   нет**: единственное описание формы ответа — `openapi.json`, проверенный на проводе.

### Клиенты

- Общими делаются **типы и константы**, а не HTTP-клиент. У web клиент серверный
  (`lib/api.ts`: `server-only`, таймауты, проброс IP посетителя), у мобильного будет свой
  (refresh-токены, повтор запросов).
- В `shared` запрещено: `server-only`, `next/*`, Node-специфичные модули, секреты,
  обращения к сети.
- Совместимость `shared` с React Native (Metro/Expo) — **гипотеза**: пакет не использует
  Node API, но сборка в Metro не проверялась. Проверить smoke-сборкой при старте
  мобильной разработки; при проблемах — добавить ESM-сборку пакета.

## Последствия

- Нет второго источника истины после PR C; расхождение схемы и реального ответа ловит e2e.
- Минус: в API появляются классы схем ответов; на этапе PR B они временно дублируют
  интерфейсы `shared` (защищено проверкой 1).

## Альтернативы

- **Только рукописные интерфейсы (как сейчас)** — нет машинного контракта для клиентов вне
  монорепозитория, OpenAPI пришлось бы писать вручную.
- **Zod-схемы в `shared` как единый источник** (валидация + типы + OpenAPI) — большой
  рефакторинг работающих DTO и валидаторов, риск регрессий в проверенном коде; не оправдан
  сейчас.
- **Сгенерированный HTTP-клиент для всех** — смешивает разные требования web и mobile.
