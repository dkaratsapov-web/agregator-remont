# ADR 0003. Общие контракты: `packages/shared` и типы из OpenAPI

**Статус:** Предложено (PR A, Issue #10). Реализация — PR B (генерация и сверка), PR C
(переход на сгенерированные типы).

## Контекст

`packages/shared` содержит две разные вещи:

1. **Константы и правила ввода**: `JOB_CATEGORIES`, `JOB_STATUSES`, `BID_STATUSES`,
   `USER_ROLES`, `JOB_LIMITS`, `BID_LIMITS`, `PROFILE_LIMITS`, `AUTH_LIMITS`, `PAGINATION`,
   русские названия. Их используют и DTO-валидаторы API, и формы web.
2. **Интерфейсы ответов**: `JobDto`, `OwnJobDto`, `UserDto`, `AuthSessionDto`, `BidDto`,
   `MyBidDto`, `JobBidDto`, `ContractorProfileDto`, `Paginated<T>`. Пишутся вручную; API
   возвращает их через явные мапперы.

Пакет не зависит от Next.js и `server-only`, собирается в CommonJS и пригоден для React
Native. После PR B появится OpenAPI — второе описание тех же ответов. Два независимых
описания — риск расхождения.

## Решение

**Источник истины для формы ответов — код API**; OpenAPI генерируется из него;
TypeScript-типы ответов для клиентов генерируются из OpenAPI. Константы остаются
рукописными в `shared` и являются источником истины для ограничений ввода.

```
packages/shared (константы, лимиты, enum'ы) ──▶ DTO-валидаторы API, формы web/mobile
API: классы схем ответов (@nestjs/swagger) ──▶ apps/api/openapi.json ──▶ сгенерированные типы
                                                                         (packages/shared/src/generated)
```

Шаги:
1. **PR B.** В API — классы схем ответов, которые `implements` существующих интерфейсов
   `shared` (компилятор не даст им разойтись). Генерация `openapi.json` и типов
   (`openapi-typescript`, только типы, без runtime). Тест на уровне типов: рукописные
   интерфейсы `shared` и сгенерированные типы взаимно присваиваемы. Расхождение ломает
   `pnpm typecheck` в CI.
2. **PR C.** Рукописные интерфейсы ответов в `shared` заменяются псевдонимами
   сгенерированных типов (`export type JobDto = components['schemas']['JobDto']`), имена
   экспортов не меняются, web не переписывается. После этого форма ответа описана в одном
   месте — в коде API.

Клиенты:
- Общими делаются **типы и константы**, а не HTTP-клиент. У web клиент серверный
  (`lib/api.ts`: `server-only`, таймауты, проброс IP посетителя), у мобильного будет свой
  (refresh-токены, повтор запросов). Общий fetch-клиент свёл бы разные требования в один
  модуль.
- В `shared` запрещено: `server-only`, `next/*`, Node-специфичные модули, секреты,
  обращения к сети.

## Последствия

- Нет второго источника истины: расхождение ловит компилятор и drift check.
- React Native импортирует `shared` без изменений.
- Минус: в API появляются классы схем ответов (дублируют интерфейсы на этапе PR B, затем
  интерфейсы становятся псевдонимами).

## Альтернативы

- **Только рукописные интерфейсы (как сейчас)** — нет машинного контракта для клиентов вне
  монорепозитория, OpenAPI пришлось бы писать вручную.
- **Zod-схемы в `shared` как единый источник** (валидация + типы + OpenAPI) — большой
  рефакторинг работающих DTO и валидаторов, риск регрессий в проверенном коде; не оправдан
  сейчас.
- **Сгенерированный HTTP-клиент для всех** — смешивает разные требования web и mobile,
  см. выше.
