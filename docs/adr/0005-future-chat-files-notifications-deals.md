# ADR 0005. Интерфейсы будущих чата, файлов, уведомлений и сделок

**Статус:** Принято как направление (Issue #10); контракты уточняются в PR D. **Только проектирование.** Ничего не реализуется
до Фазы 2; PR D уточняет контракты и backlog, реализация идёт вместе с функциями Фазы 2.
Таблицы, маршруты и названия ниже — предварительные.

## Общие правила для всех модулей

- Права проверяет API на каждом запросе; чужой ресурс → 404.
- Тест «пользователь А не читает и не меняет ресурс Б» для каждого маршрута.
- Изменения состояния — в транзакции с журналом изменений (`audit_logs`), с блокировками по
  графу `docs/SECURITY.md` 6.3.
- Повтор запроса после обрыва сети не создаёт дубликат: `clientMessageId` для сообщений,
  заголовок `Idempotency-Key` для остальных созданий (ключ + пользователь + маршрут хранятся
  24 часа вместе с ответом).
- Списки, которые растут без предела, — курсорная пагинация (`?before=<cursor>&limit`),
  сортировка `(createdAt, id)`.
- Персональные данные (152-ФЗ): хранение данных пользователей — на серверах в РФ; в push,
  логи и аналитику содержимое и ПДн не попадают. Юридическая проверка — до запуска,
  в рамках гейта «право, ПДн, безопасность» (`docs/MOBILE_READINESS_AUDIT.md`, 9.1): политика
  хранения и удаления, роль зарубежных push-провайдеров, жалобы и abuse.

## Сообщения (чат)

- Данные: `conversations` (привязка к заказу и отклику), `conversation_members`
  (пользователь, `lastReadMessageId`), `messages` (`senderId`, текст, `clientMessageId`
  уникален в паре с отправителем, `createdAt`).
- Когда создаётся диалог (после отклика или после выбора исполнителя) — продуктовое решение
  владельца; от него зависит, когда раскрываются контакты.
- Маршруты: `GET /v1/me/conversations`, `GET /v1/me/conversations/:id/messages?before=`,
  `POST /v1/me/conversations/:id/messages` (повтор с тем же `clientMessageId` возвращает уже
  созданное сообщение), `POST /v1/me/conversations/:id/read`.
- Доставка: сначала polling открытого диалога; WebSocket/SSE — только при реальной
  потребности. Push — лишь сигнал «есть новое».
- Защита: членство проверяется в каждом запросе к БД (`WHERE member`), лимиты на отправку,
  модерация и жалобы (release gate 8), фильтр контактов до этапа, когда их раскрытие
  разрешено.

## Файлы и фото

- S3-совместимое хранилище, бакет приватный, отдельный домен для файлов (без cookie сайта).
- Загрузка: `POST /v1/me/uploads {purpose, contentType, size}` → сервер проверяет доступ,
  размер, квоту → presigned `PUT` на 5 минут с жёсткими `Content-Type` и
  `Content-Length` → клиент загружает напрямую → `POST /v1/me/uploads/:id/complete` →
  сервер проверяет тип **по сигнатуре** (JPEG, PNG, WebP, HEIC; PDF — по решению),
  перекодирует изображения с удалением EXIF (геолокация), при необходимости антивирус,
  статус `READY`.
- Скачивание: `GET /v1/files/:id` → проверка доступа → presigned `GET` на 1–5 минут;
  не-изображения — с `Content-Disposition: attachment`.
- Запрещены SVG, HTML и всё, что браузер может исполнить.
- Лимиты: размер файла, число файлов на заказ/сделку, суточная квота.
- Удаление и хранение: мягкое удаление, физическое удаление по сроку; незавершённые загрузки
  чистятся через 24 часа.

## Уведомления

- Доменные события (`BID_CREATED` → владельцу заказа, `BID_ACCEPTED` → подрядчику,
  `MESSAGE_CREATED` → участникам) записываются в таблицу outbox **в той же транзакции**,
  что и изменение. Отдельный обработчик доставляет их по каналам: in-app, email, push.
- Защита от дублей: уникальный ключ (событие, получатель, канал). Настройки пользователя,
  лимиты и дайджесты против спама.
- Push-токены устройств: `PUT /v1/me/push-token {token, platform, provider}` привязывает
  токен к **текущей сессии**; отзыв сессии и выход удаляют токен; недействительные токены
  удаляются по ответу провайдера. Чужой токен не регистрируется повторно на другого
  пользователя без отвязки.
- Содержимое push — без ПДн и текста сообщений («Новое сообщение по заказу»), чтобы ничего
  не утекало на экран блокировки; подробности приложение получает через API после входа.
- FCM/APNs (и, возможно, RuStore Push для устройств без сервисов Google) сейчас не
  подключаются; выбор — отдельное решение.

## Сделки (без денег)

- Конечный автомат на API, например: `AGREED → IN_PROGRESS → COMPLETED`, а также
  `CANCELLED`, `DISPUTED`. Каждый переход: кто имеет право (роль и участие), из какого
  статуса, блокировка строки, запись в журнал, тест на каждый запрещённый переход.
- Связь с текущей моделью: выбор исполнителя уже переводит заказ в `IN_PROGRESS`; сделка
  станет отдельной сущностью, а не новым смыслом статусов заказа.
- Платежи, escrow, выплаты — **только Фаза 3**: сторонний провайдер, sandbox, юридическая и
  security-проверка. В сделках Фазы 2 нет сумм к оплате и платёжных статусов.

## Последствия

- Клиенты получают одинаковые интерфейсы; мобильные особенности (push, повтор при обрыве
  сети) учтены заранее, без мёртвого кода сейчас.

## Альтернативы

- **WebSocket с первого дня** — сложнее эксплуатация (sticky-сессии, масштабирование), не
  нужен при текущем объёме.
- **Загрузка файлов через API** — нагрузка на API и риск обхода лимитов; presigned URL
  проще и безопаснее.
- **Push с текстом сообщения** — удобно, но раскрывает содержимое на экране блокировки и
  передаёт ПДн третьим сторонам.
