# Безопасность: решения, исключения и гейты

Документ ведёт Claude Code; обновляется в каждом PR, который меняет что-то из перечисленного.
Это не формальный аудит безопасности.

## 1. Исключения по зависимостям

Проверка в CI: `pnpm audit --prod --audit-level high` (блокирующая). Обновления зависимостей
отслеживает Dependabot (`.github/dependabot.yml`, еженедельно, npm и GitHub Actions).

## 2. Rate limit

- `@nestjs/throttler`, 120 запросов в минуту на IP, `/health` исключён.
- **Ограничение: только один инстанс API.** Счётчики хранятся в памяти процесса; при нескольких
  репликах лимит фактически умножается на число реплик, а перезапуск сбрасывает счётчики.
- IP клиента берётся из `req.ip`, который зависит от `TRUST_PROXY` (см. `docs/DEPLOYMENT.md`).
  Без правильной настройки за прокси все клиенты делят один лимит (IP прокси).
- Перед масштабированием: общий storage для throttler (Redis), лимиты по пользователю/ключу
  для авторизованных запросов, отдельные строгие лимиты на write-эндпоинты.

## 3. Content-Security-Policy

Текущее состояние: `Content-Security-Policy-Report-Only` (`apps/web/src/lib/csp.ts`).

```
default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline';
img-src 'self' data: blob:; font-src 'self'; connect-src 'self'; manifest-src 'self';
worker-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'
```

- В production нет `unsafe-eval` (проверяется unit-тестом и smoke-тестом в CI). В dev
  добавляются `unsafe-eval` и `ws:` для HMR.
- Проверено в Chromium (Playwright) на `/`, `/jobs`, фильтре, карточке, 404 и `/offline`:
  0 нарушений, service worker регистрируется.

План перехода на enforce (до публичного релиза):
1. Добавить сбор отчётов (`report-to`/`report-uri`) на собственный эндпоинт и наблюдать.
2. Перейти на nonce: генерация в `proxy.ts` (бывший middleware), `script-src 'self' 'nonce-…' 'strict-dynamic'`,
   убрать `'unsafe-inline'` из `script-src`. Учесть, что nonce делает все страницы динамическими.
3. Переключить заголовок на `Content-Security-Policy`, добавить `upgrade-insecure-requests`.
4. Smoke-тест: заголовок enforce присутствует, страницы рендерятся без нарушений.

## 4. CORS

- Web получает данные с сервера (React Server Components), поэтому браузерный CORS ему не нужен.
- `CORS_ORIGINS` пуст по умолчанию: браузерам с чужих origin ответы API недоступны.
- Каждый элемент проверяется как точный origin; `*`, пути, слэш в конце и не-http(s) схемы
  запрещены; в `NODE_ENV=production` разрешён только `https`. Ошибка конфигурации = API не стартует.
- **CORS не является авторизацией**: он ограничивает только браузеры. Защита данных обязана
  быть на сервере (раздел 5).

## 5. Гейт для write-эндпоинтов (Фаза 1)

Ни один эндпоинт, изменяющий данные, не мержится без выполнения всех пунктов:

1. **Аутентификация** на сервере; сессии/токены с ограниченным сроком, cookie `HttpOnly`,
   `Secure`, `SameSite`; защита от CSRF для cookie-сессий.
2. **RBAC на сервере**: роль берётся только из серверной сессии/БД, никогда из тела запроса,
   заголовков или query.
3. **Проверка владения ресурсом** (заказчик меняет только свои заказы, подрядчик только свои
   отклики) в сервисном слое, не только в контроллере.
4. **Валидация** DTO с whitelist, лимиты длины, серверный пересчёт производных полей;
   массовое присваивание запрещено (явные поля в `data`).
5. **Анти-спам и лимиты**: отдельные строгие rate limit на запись, лимиты количества
   (например, откликов в сутки).
6. **Файлы**: проверка типа по сигнатуре, лимит размера, серверные имена, приватное
   хранилище с выдачей по подписанным ссылкам после проверки доступа; SVG/HTML запрещены.
7. **Audit log** изменений: кто, что, когда, старое/новое значение, без секретов и лишних ПДн.
8. **Тесты**: unit и integration на каждый запрет (чужой ресурс → 403/404, неверная роль → 403,
   без сессии → 401), а не только на успешные сценарии.
9. **Персональные данные**: минимизация, публичные ответы без контактов и ПДн, отдельные
   DTO для публичной и приватной выдачи.

## 6. Деньги

Реальные платежи, escrow и хранение денег не реализуются до отдельного этапа с подтверждённой
схемой платёжного провайдера, юридической проверкой и независимым security-тестированием
(`docs/ROADMAP.md`, Фаза 3).
