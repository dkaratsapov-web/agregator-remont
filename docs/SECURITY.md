## 2. Rate limit

- `@nestjs/throttler`, 120 запросов в минуту на IP, `/health` исключён.
- **Ограничение: только один инстанс API.** Счётчики хранятся в памяти процесса; при нескольких
  репликах лимит фактически умножается на число реплик, а перезапуск сбрасывает счётчики.
- IP клиента берётся из `req.ip`, который зависит от `TRUST_PROXY` (см. `docs/DEPLOYMENT.md`).
  Без правильной настройки за прокси все клиенты делят один лимит (IP прокси).
- Перед масштабированием: общий storage для throttler (Redis), лимиты по пользователю/ключу
  для авторизованных запросов, отдельные строгие лимиты на write-эндпоинты.

## 3. Content-Security-Policy

Текущее состояние: `Content-Security-Policy-Report-Only` (`apps/web/src/lib/csp.ts`) со своим
nonce на каждый ответ. Его выдаёт `apps/web/src/proxy.ts` на каждый запрос страницы без тела
(GET): политика уходит в ответ и в заголовки запроса, откуда Next.js берёт nonce для своих
скриптов. Загруженные ими модули разрешает `'strict-dynamic'`. Встроенный скрипт без nonce
(например, внедрённый через XSS) нарушает политику; `'unsafe-inline'` в `script-src` больше нет
(независимый аудит, AUD-02). Все страницы рендерятся на запрос (`connection()` в корневом layout):
в заранее собранный HTML nonce не вписать; статическими раньше были только `/privacy`,
`/offline` и страницы ошибок.

```
default-src 'self'; script-src 'self' 'nonce-<16 байт base64>' 'strict-dynamic'; style-src 'self' 'unsafe-inline';
img-src 'self' data: blob:; font-src 'self'; connect-src 'self'; manifest-src 'self';
worker-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none';
report-uri /csp-report
```

- В production нет `unsafe-eval` (проверяется unit-тестом и smoke-тестом в CI). В dev
  добавляются `unsafe-eval` и `ws:` для HMR.
- Smoke-тест CI проверяет: в `script-src` есть nonce и нет `unsafe-inline`, скрипты страницы
  несут nonce, у нового ответа он другой. Unit-тесты — `csp.test.ts`, `proxy.test.ts`.
- `style-src` пока с `'unsafe-inline'`: встроенные стили React и анимаций; стили не исполняют код.
- Запросы с телом (`Content-Length` или `Transfer-Encoding`: Server Actions, загрузка фото,
  `POST /lead`) идут мимо proxy. Иначе Next.js копирует тело для proxy, обрезает его после 10 МБ
  (`proxyClientMaxBodySize`, фото — до 27 МБ) и ждёт его целиком, прежде чем ответить: открытый
  `POST /lead` читал бы 8 МБ вместо мгновенного 503 (проверка в CI-задаче proxy).
- Но ответ на такой запрос тоже может быть HTML-страницей: форма без JS или любой POST на адрес
  страницы рендерит её целиком. Им `next.config.ts` ставит строгую политику без nonce: только
  файлы скриптов со своего адреса, встроенные скрипты запрещены (`script-src 'self'`; `'none'`
  нельзя — браузер без JS всё равно загружает файлы по `<link rel="preload">`, и это нарушение
  поймали браузерные сценарии). Страница ответа на форму без JS и так работает без JS. Без
  этого правила HTML-ответ на POST шёл бы вообще без CSP — обход политики (найдено агентом
  проверки, `docs/REVIEW_AGENT.md`). Правила proxy и next.config не пересекаются: proxy — только
  без `Content-Length`/`Transfer-Encoding`, правило — только с ними. Тест matcher вызывает функции
  самого Next.js (`proxy.test.ts`).
- Проверено в Chromium (Playwright) на `/`, `/jobs`, фильтре, карточке, 404 и `/offline`:
  0 нарушений, service worker регистрируется.

- **Все браузерные сценарии CI проверяют отсутствие нарушений** (`scripts/lib/csp-watch.mjs`):
  сценарий собирает сообщения CSP из консоли всех вкладок и падает, если они есть. Это 13
  сценариев, Chromium и WebKit, гость, заказчик, подрядчик и администратор, с JS и без. Сторож
  проверен намеренным нарушением: чужая картинка и чужой скрипт пойманы.
- **Отчёты настоящих браузеров** приходят на `POST /csp-report` (`apps/web/src/app/csp-report`)
  и пишутся в журнал web строкой `{"event":"csp-violation",…}`. Без данных людей: директива,
  источник без пути и параметров, путь страницы без query и с замаскированными токенами.
  Не больше 60 строк в минуту на процесс, отброшенные считаются строкой
  `csp-violation-dropped`. В закрытом тесте адрес за паролем тестировщика (новых открытых
  адресов в Caddy нет). Посмотреть на сервере:
  `docker compose logs web --since 168h | grep csp-violation`.

План перехода на enforce (до публичного релиза):
1. ~~Сбор отчётов на собственный адрес~~ — сделано (`report-uri /csp-report`). Дальше —
   неделя закрытого теста без строк `csp-violation` в журнале web.
2. ~~Перейти на nonce~~ — сделано (`proxy.ts`, `script-src 'self' 'nonce-…' 'strict-dynamic'`,
   без `'unsafe-inline'`), пока в режиме report-only. Дальше — неделя закрытого теста с nonce
   без строк `csp-violation` в журнале web.
3. Переключить заголовок на `Content-Security-Policy`, добавить `upgrade-insecure-requests`
   (решение владельца: после этого шаг блокирует, а не только сообщает).
4. Smoke-тест: заголовок enforce присутствует, страницы рендерятся без нарушений.

## 4. CORS

- Web получает данные с сервера (React Server Components), поэтому браузерный CORS ему не нужен.
- `CORS_ORIGINS` пуст по умолчанию: браузерам с чужих origin ответы API недоступны.
- Каждый элемент проверяется как точный origin; `*`, пути, слэш в конце и не-http(s) схемы
  запрещены; в `NODE_ENV=production` разрешён только `https`. Ошибка конфигурации = API не стартует.
- **CORS не является авторизацией**: он ограничивает только браузеры. Защита данных обязана
  быть на сервере (раздел 6).

## 5. Аутентификация (Фаза 1, PR «auth»)

Реализовано:

- **Пароли**: argon2id (`@node-rs/argon2`, m=19 MiB, t=2, p=1 по OWASP), длина 10..128
  символов (верхняя граница защищает от DoS дорогим хешированием), пароль не может совпадать
  с email. Хеш никогда не попадает в ответы API (явный whitelist `toUserDto`).
- **Сессии**: случайный токен 32 байта (base64url), в БД хранится только SHA-256, срок 30 дней,
  выход удаляет только текущую сессию, истёкшие сессии пользователя чистятся при входе.
- **Роль** берётся только из БД по сессии. `ADMIN` нельзя получить регистрацией
  (`@IsIn(['CUSTOMER','CONTRACTOR'])`), лишние поля запроса отклоняются.
- **Вход**: одинаковый ответ 401 «Неверный email или пароль» для неверного пароля и
  несуществующего email; для несуществующего email всё равно выполняется проверка пароля
  по хешу-заглушке, чтобы время ответа не раскрывало регистрацию.
- **Регистрация** честно сообщает «email уже зарегистрирован» (409): это раскрывает факт
  регистрации, но без подтверждения email иначе нельзя; ограничено rate limit.
- **Rate limit**: вход и регистрация 10 запросов/мин на IP (`AUTH_RATE_LIMIT_PER_MIN`),
  поверх общего лимита.
- **Регистрация атомарна**: пользователь и первая сессия создаются в одной транзакции
  (сбой записи сессии не оставляет аккаунт, на который потом пришёл бы 409).
- **Web**: токен лежит в cookie `__Host-ar_session` (`HttpOnly`, `Secure`, `SameSite=Lax`,
  `Path=/`), JavaScript к нему доступа не имеет. В API токен передаётся сервером web как
  `Authorization: Bearer`, поэтому CSRF к самому API неприменим.
- **CSRF для Server Actions** (вход, регистрация, выход): `SameSite=Lax` не считается
  достаточной защитой. Два слоя:
  1. Next.js отклоняет action, если `Origin` не совпадает с хостом (`X-Forwarded-Host`/`Host`).
     `serverActions.allowedOrigins` **не задан** намеренно: разрешён только собственный origin.
  2. Собственная проверка `isSameOriginRequest` в каждом action: `Origin` обязателен (Next.js
     пропускает запрос без `Origin` с предупреждением), `Origin: null` отклоняется,
     `Sec-Fetch-Site` при наличии должен быть `same-origin`. `Origin` сравнивается строго с
     `WEB_PUBLIC_ORIGIN` (обязателен в production, иначе web не стартует), поэтому заголовки
     `Host`/`X-Forwarded-Host` в проверке не участвуют и их подмена ничего не даёт: интеграционный
     тест подтверждает, что запрос с чужим `Origin` и совпадающим с ним поддельным
     `X-Forwarded-Host` проходит проверку Next.js, но отклоняется нашей.

  Подтверждено тестами: unit (`same-origin.test.ts`, 11 кейсов), тесты actions с подменой
  заголовков (`actions.test.ts`) и интеграционный тест на production-сборке
  (`scripts/auth-integration.mjs`, в CI): вход с чужим `Origin`, `Origin: null` и без `Origin`
  не создаёт сессию.
- **Выход** удаляет cookie только после подтверждения API (204, либо 401 — сессия уже
  недействительна). При сбое API (5xx, таймаут) пользователь остаётся в аккаунте и видит
  «Не удалось выйти»: иначе он считал бы, что вышел, а токен действовал бы до 30 дней.
  Покрыто тестами actions и интеграционным тестом с остановленным API.
- **Редирект после входа** (`?next=`) только на относительные пути этого сайта
  (`safeRedirectPath`, покрыто тестами на `//evil`, `/\evil`, схемы, управляющие символы).
- **IP посетителя для лимитов**: Next.js сохраняет `X-Forwarded-For` от клиента, поэтому web
  берёт адрес на позиции, которую дописал доверенный proxy (`WEB_TRUST_PROXY_HOPS`), проверяет
  его `node:net.isIP` (IPv4-mapped IPv6 приводится к IPv4) и передаёт API; API доверяет
  заголовку только от адресов из `TRUST_PROXY`. При `WEB_TRUST_PROXY_HOPS=0` IP не передаётся
  (подмену исключает, но лимит становится общим для всех посетителей web).
  Подтверждено: API e2e (`client-ip-rate-limit.e2e-spec.ts`: раздельные лимиты для двух
  посетителей, подделка начала цепочки не сбрасывает лимит, без `TRUST_PROXY` заголовок
  игнорируется) и интеграционный тест proxy → web → API в CI.

### Условия публичного запуска регистрации (release gate)

Текущая аутентификация допустима для закрытого тестирования на одном инстансе.
**Не production-ready**, пока не выполнено:

1. Распределённый rate limit (общее хранилище, например Redis) вместо счётчиков в памяти.
2. Защита от перебора по аккаунту/идентичности, а не только по IP (перебор с многих адресов),
   с защитой от abuse-lockout: атакующий не должен блокировать вход владельцу аккаунта
   (прогрессивные задержки, CAPTCHA после порога, а не жёсткая блокировка).
   **Сделано (PR #47), кроме CAPTCHA.** Серия неверных паролей к одному адресу с любых IP:
   - первые 5 подряд — без паузы, дальше перед каждой попыткой пауза 2, 4, 8 … до 60 с
     (`LOGIN_THROTTLE`, `apps/api/src/auth/login-throttle.ts`);
   - ответ — 429 `LOGIN_THROTTLED` с `Retry-After`, пароль во время паузы не проверяется;
   - попытка занимается до проверки пароля одним запросом под блокировкой строки серии
     (`LoginThrottle.attempt`): пачка одновременных запросов в момент окончания паузы
     проверяет пароль один раз, а не каждый запрос пачки;
   - потолок — пауза, а не блокировка: подбор ограничен одной попыткой в минуту, владелец ждёт
     не дольше минуты;
   - учёт по SHA-256 адреса, одинаково для несуществующих аккаунтов: ответ не раскрывает
     регистрацию, сам адрес не хранится;
   - серию обнуляет верный пароль или 15 минут без попыток;
   - та же серия считает неверный текущий пароль при смене пароля в кабинете
     (`POST /v1/me/password`): завладевший открытой сессией не подберёт пароль через смену
     быстрее, чем через вход.

   CAPTCHA после порога — нужен провайдер (решение владельца). Тесты —
   `login-throttle.e2e-spec.ts`.
3. Подтверждение email и восстановление пароля (нужен SMTP-провайдер).
4. Отзыв всех сессий при смене/сбросе пароля и по событию безопасности; «выйти на всех устройствах».
   **Сделано:**
   - смена пароля в кабинете завершает все остальные входы, текущий остаётся
     (`account.e2e-spec.ts`, «changes the password, keeps this session and ends the others»);
   - сброс по ссылке завершает все входы (`accounts.e2e-spec.ts`, «a link works once, ends every
     session…»);
   - блокировка администратором завершает все входы, и база не даёт создать новый
     (`moderation.e2e-spec.ts`, `accounts.e2e-spec.ts`, «no new session for a blocked account…»);
   - «Завершить остальные сеансы» и завершение одного сеанса — в настройках кабинета
     (`account.e2e-spec.ts`, «revokes all other sessions»).

   Пароль для «выйти на всех устройствах» в мобильной схеме (`MOBILE_AUTH_DESIGN.md`, решение 4)
   — вместе с мобильной авторизацией.
5. Периодическая очистка истёкших сессий. **Сделано (PR #47):** `CleanupService` раз в
   `CLEANUP_INTERVAL_MIN` минут (по умолчанию 60; 0 — выключено) удаляет:
   - истёкшие сессии;
   - ссылки сброса пароля, использованные или просроченные больше недели назад;
   - закончившиеся серии неверных паролей.

   Удаления идемпотентны, несколько экземпляров API друг другу не мешают.
6. Проверка паролей по базам утечек (HIBP k-anonymity) — желательно.
7. Повторная аутентификация для смены email/пароля. **Сделано для пароля:** смена требует
   текущий пароль, он проверяется под блокировкой строки пользователя (SEC-5) и с паузой после
   серии ошибок (п. 2). Смены email в продукте нет; при её появлении — тот же порядок плюс
   подтверждение нового адреса (нужна почта, п. 3).
8. Модерация публичного контента и жалобы: описание заказа вводится пользователем, и подсказка
   «не указывать контакты» не мешает опубликовать персональные данные. Нужны правила продукта
   (фильтр телефонов и адресов, жалобы, снятие с публикации) до публичного запуска.
9. Эксплуатация до реальных данных: резервные копии по расписанию вне сервера с регулярной
   проверкой восстановления, мониторинг доступности и срока сертификата, ограничение размера
   логов (`deploy/README.md`).

## 6. Гейт для write-эндпоинтов (Фаза 1)

Ни один эндпоинт, изменяющий данные, не мержится без выполнения всех пунктов:

1. **Аутентификация** на сервере; сессии/токены с ограниченным сроком, cookie `HttpOnly`,
   `Secure`, `SameSite`; защита от CSRF для cookie-сессий.
2. **RBAC на сервере**: роль берётся только из серверной сессии/БД, никогда из тела запроса,
   заголовков или query.
3. **Проверка владения ресурсом** (заказчик меняет только свои заказы, подрядчик только свои
   отклики) в сервисном слое, не только в контроллере.
4. **Валидация** DTO с whitelist, лимиты длины, серверный пересчёт производных полей;
   массовое присваивание запрещено (явные поля в `data`).
5. **Анти-спам и лимиты**: отдельные строгие rate limit на запись, лимиты количества
   (например, откликов в сутки).
6. **Файлы**: проверка типа по сигнатуре, лимит размера, серверные имена, приватное
   хранилище с выдачей по подписанным ссылкам после проверки доступа; SVG/HTML запрещены.
7. **Audit log** изменений: кто, что, когда, старое/новое значение, без секретов и лишних ПДн.
8. **Тесты**: unit и integration на каждый запрет (чужой ресурс → 403/404, неверная роль → 403,
   без сессии → 401), а не только на успешные сценарии.
9. **Персональные данные**: минимизация, публичные ответы без контактов и ПДн, отдельные
   DTO для публичной и приватной выдачи.

### 6.1 Выполнение гейта: заказы заказчика (`/v1/me/jobs`, Фаза 1.2)

| # | Пункт | Как выполнен |
| --- | --- | --- |
| 1 | Аутентификация, CSRF | `SessionGuard` на всём контроллере; Server Actions проверяют `Origin` (раздел 5). |
| 2 | RBAC | `@Roles('CUSTOMER')` + `RolesGuard` после `SessionGuard`; роль из БД. Подрядчик и администратор получают 403. |
| 3 | Владение | Каждый запрос в `MyJobsService` фильтрует `ownerId = текущий пользователь`; чужой и несуществующий заказ одинаково дают 404 (наличие не раскрывается). Демо-заказы без владельца никому не доступны для правки. Правка и закрытие блокируют строку заказа (`SELECT … FOR UPDATE`) до чтения состояния: параллельные изменения одного заказа выполняются по очереди, правка после закрытия невозможна (409). |
| 4 | Валидация, массовое присваивание | DTO с whitelist и `forbidNonWhitelisted`: `ownerId`, `status`, `id`, даты в теле → 400. Длины из `JOB_LIMITS`, запрет управляющих и bidi-символов, бюджет целым числом 0..10⁹, `min ≤ max` проверяется и для объединённых значений при правке (плюс CHECK в БД). В `data` попадают только явно перечисленные поля. |
| 5 | Лимиты | Отдельный throttler `write` (`WRITE_RATE_LIMIT_PER_MIN`, 30/мин на IP) и не больше 20 новых заказов на пользователя за сутки (429). Квота атомарна: создание блокирует строку пользователя (`FOR UPDATE`), поэтому параллельные запросы считают её по очереди (тест: 6 параллельных POST при 18 заказах → ровно 2 созданы). |
| 6 | Файлы | Не применимо: загрузки файлов пока нет. |
| 7 | Audit log | Таблица `audit_logs`: автор, действие (`JOB_CREATED`, `JOB_UPDATED`, `JOB_CLOSED`), сущность, изменённые поля «было/стало», время. Запись в той же транзакции, что и изменение, под блокировкой строки, поэтому «было» всегда равно предыдущему «стало» (тест: 8 параллельных правок дают непрерывную цепочку). Чтения журнала через API пока нет (будет в админке). |
| 8 | Негативные тесты | API e2e: без сессии → 401 (4 маршрута), подрядчик → 403, чужой заказ → 404 на чтение/правку/закрытие, демо-заказ → 404, подстановка `ownerId`/`status`/`id`/`createdAt` → 400, 13 кейсов валидации, суточный лимит → 429, закрытый заказ → 409, throttler → 429. Конкурентность (`my-jobs-concurrency.e2e-spec.ts`): параллельные правки, правка против закрытия, параллельные закрытия, квота при параллельных созданиях; на коде без блокировок два из четырёх тестов падают. Интеграционный тест web → API в CI: чужой заказчик → 404, подрядчик → 403, чужой `Origin` (в т.ч. с подделанным `X-Forwarded-Host`) не создаёт заказ. |
| 9 | Персональные данные | Публичный `JobDto` не содержит `ownerId`/данных владельца (тест). В описании заказа подсказка не указывать телефон и адрес. |

### 6.2 Выполнение гейта: профили подрядчиков и отклики (Фаза 1.3)

| # | Пункт | Как выполнен |
| --- | --- | --- |
| 1 | Аутентификация, CSRF | `SessionGuard` на всех маршрутах; Server Actions проверяют `Origin` по `WEB_PUBLIC_ORIGIN` (интеграционный тест: выбор исполнителя с чужим `Origin` и поддельным `X-Forwarded-Host` отклоняется). |
| 2 | RBAC | Профиль, отклик, свои отклики, отзыв — только `CONTRACTOR`; список откликов на заказ и выбор исполнителя — только `CUSTOMER`. Заказчик не может откликнуться (403), подрядчик не видит отклики на заказ (403). |
| 3 | Владение | Подрядчик видит и отзывает только свои отклики (`contractor_id = текущий пользователь`, чужой → 404). Отклики на заказ видит только владелец заказа (чужой заказ → 404). Выбрать можно только отклик на этот же заказ (отклик на другой заказ через свой → 404). |
| 4 | Валидация, массовое присваивание | Whitelist DTO: `status`, `contractorId`, `jobId`, `userId` в теле → 400. Цена целым числом 0..10⁹, срок 1..365 дней, комментарий 10..2000 без управляющих/bidi-символов; профиль: категории из списка без повторов, до 10 городов (trim, дубликаты убираются), опыт 0..70. CHECK-ограничения в БД для цены, срока и опыта. |
| 5 | Лимиты | Один отклик подрядчика на заказ (уникальный индекс, 409); не больше 30 откликов в сутки (атомарно, блокировка строки пользователя); throttler `write`. Отклик только на открытый заказ (409). |
| 6 | Файлы | Не применимо. |
| 7 | Audit log | `BID_CREATED`, `BID_WITHDRAWN`, `BID_ACCEPTED`, `BID_REJECTED`, `JOB_STARTED`, `PROFILE_UPDATED` в той же транзакции. Изменения профиля сериализуются блокировкой строки пользователя, «было/стало» — содержимое профиля до и после (тест: 8 параллельных сохранений, включая первое создание, образуют непрерывную цепочку; на коде без блокировки тест падает). |
| 8 | Негативные тесты и конкурентность | API e2e: 401/403/404/409/400/429 на всех маршрутах. Конкурентность: 5 параллельных выборов разных откликов → ровно один исполнитель; выбор и отзыв одного отклика → ровно одно действие успешно, состояние соответствует; выбор и отзыв другого отклика → отзыв не перезаписывается «отклонён», журнал соответствует; новые отклики во время выбора → после выбора нет ожидающих; квота при параллельных откликах. Частичный уникальный индекс в БД запрещает двух выбранных исполнителей на заказ. Отрицательный контроль: без блокировок падает тест «выбор и отзыв одного отклика»; гонку «отзыв другого отклика против массового отклонения» тест на этой нагрузке не воспроизводит — защита (блокировка `FOR UPDATE` с перепроверкой статуса) есть, но тестом не доказана. |
| 9 | Персональные данные | Заказчик видит имя и профиль подрядчика, но не email и не идентификатор пользователя (тест). Отклики не видны в публичных данных заказа и другим подрядчикам. Подсказки «не указывать контакты» в профиле и отклике; модерация — условие публичного запуска. |

### 6.3 Граф блокировок

Единый порядок: **пользователь → заказ → отклик**. Каждая операция берёт подмножество этой
цепочки строго в этом порядке, поэтому циклы ожидания (взаимоблокировки) невозможны:

| Операция | Блокировки |
| --- | --- |
| Создание заказа | пользователь (`FOR UPDATE`, суточная квота) |
| Правка / закрытие заказа | заказ (`FOR UPDATE`) → при закрытии ожидающие отклики (`FOR UPDATE`) |
| Профиль подрядчика | пользователь (`FOR UPDATE`) |
| Создание отклика | пользователь (`FOR UPDATE`, квота) → заказ (`FOR SHARE`) |
| Выбор исполнителя | заказ (`FOR UPDATE`) → выбранный отклик → остальные ожидающие (`FOR UPDATE`) |
| Отзыв отклика | только отклик (`FOR UPDATE`); после него ничего не блокируется |

Новые операции обязаны соблюдать этот порядок. Ограничение тестов: конкурентные e2e
подтверждают ключевые чередования, но не доказывают все возможные (см. 6.2, п. 8).

## 8. Публичная главная при закрытом тестировании

Главная (`/`) открыта без пароля, всё остальное приложение доступно только тестировщикам
(`deploy/Caddyfile`, matcher `@private` и `forward_auth`). Условия, при которых это допустимо:

- На главной нет данных приложения. Если в браузере есть cookie сессии, сервер один раз
  спрашивает API (`GET /v1/me`), кто вошёл, и показывает этому же пользователю его имя и меню
  кабинета; в клиентские компоненты передаются только имя и роль. Без cookie к API не
  обращается. Страница динамическая (`ƒ`), ответ не кешируется (`private, no-store`).
- Без пароля разрешено только чтение (GET, HEAD). Next.js принимает Server Actions
  POST-запросом на любой адрес по их идентификатору (идентификаторы есть в открытых файлах
  `/_next/static`), поэтому POST на `/` мог бы запустить вход, регистрацию или действия кабинета
  в обход пароля. Matcher `@private` закрывает паролем любой метод, кроме GET и HEAD, на всех
  адресах, в том числе на открытых. Исключения — два Route Handler (не Server Actions):
  `POST /lead` (заявка) и `POST /gate/login` (форма входа тестировщика).
- Ссылки с главной в приложение — обычные `<a href>`, без prefetch: открытая страница ничего
  не запрашивает из закрытой части.
- Без пароля также доступны: `/privacy` (статичный текст политики без данных приложения),
  `/gate` (страница входа тестировщика), `/offline` (статичная офлайн-страница для service worker),
  `/sw.js`, `/robots.txt`, `/manifest.webmanifest`, иконки и `/_next/static/*`. Последнее —
  неизменяемые сборочные файлы всего фронтенда: в них код интерфейса (и тексты страниц
  приложения), но нет данных, секретов и серверного кода. `/_next/image` закрыт.
- Вход тестировщика — своя страница `/gate` в стиле сайта вместо системного окна basic auth
  (его вид сайт изменить не может). Устройство (`apps/web/src/lib/gate.ts`):
  - Caddy перед каждым запросом в закрытую часть вызывает `GET /gate/check` у web
    (`forward_auth`) и пересылает cookie. Ответ 2xx — запрос идёт дальше; иначе ответ проверки
    уходит посетителю: открытие страницы в браузере (Sec-Fetch-Mode: navigate или Accept
    text/html, без RSC) — 303 на `/gate?next=<путь>`, всё остальное — пустой 401 без
    `WWW-Authenticate`. Адрес возврата проходит `safeRedirectPath` (только пути этого сайта).
    Служебные заголовки Next.js (`RSC`, `Next-Router-*`, `Next-Url`, `Next-Action`) в запрос
    проверки не пересылаются: с `RSC` Next.js сам отвечает 307 на `?_rsc`, и вместо 401 посетитель
    получал бы редирект (это ловит проверка RSC-запросов в CI).
  - Форма `/gate` отправляется обычным POST на `/gate/login`: источник формы — этот же сайт
    (Origin и Sec-Fetch-Site против хоста запроса), тело до 2 КБ, логин сравнивается за
    постоянное время, пароль — bcrypt против того же `BASIC_AUTH_HASH`, что был у basic auth.
    Не больше 10 неудачных попыток с одного IP за 15 минут (счётчик в памяти web; при
    перезапуске сбрасывается, перебор дополнительно замедляет bcrypt, ~1 с на попытку).
  - Пропуск — cookie `__Host-ar_gate` (HttpOnly, Secure, SameSite=Lax, 30 дней) вида
    `v1.<срок>.<HMAC-SHA256>`; ключ HMAC выводится из `BASIC_AUTH_HASH`, поэтому смена пароля
    тестировщика отзывает все пропуска. Следствие: кто знает `BASIC_AUTH_HASH`, может выпустить
    пропуск без пароля — хеш хранится только в `deploy/.env` на сервере и в окружении
    контейнеров web (раньше — Caddy), как и прочие секреты.
  - Без `BASIC_AUTH_USER`/`BASIC_AUTH_HASH` в окружении web вход выключен и закрытая часть
    закрыта для всех (fail closed).
- Лимит входа тестировщика: 10 неудачных попыток за 15 минут с одного IP (за Caddy —
  `WEB_TRUST_PROXY_HOPS=1`, задаётся в `docker-compose.proxy.yml`). Попытка учитывается до
  проверки пароля, синхронно: одновременные запросы не обходят лимит. Одновременных проверок
  bcrypt не больше четырёх на процесс web, сверх — ответ «занято» без проверки (поток запросов не
  займёт процессор). Тест: `apps/web/src/app/gate/login/route.test.ts`.
- Service worker: навигация (GET) идёт в сеть через SW; при сетевой ошибке отдаётся `/offline`
  (на `navigator.onLine` не опираемся: он бывает true без доступа к сайту). Переход на `/gate` —
  обычный редирект. Не-GET навигации SW не трогает.
- Проверки в CI:
  - `Docker stack behind Caddy (proxy)`: главная и её статика 200 без пароля; вход,
    регистрация, кабинет, каталог, `/_next/image`, неизвестные адреса 401, тело 401 пустое;
    HEAD и RSC-запросы к приложению 401; обход через `..`, `%2e`, `%2f`, двойное кодирование,
    регистр, `;`, `/./`, `//` не отдаёт страниц приложения; на главной нет данных приложения;
    POST, PUT, PATCH, DELETE и OPTIONS на открытые адреса (в том числе с заголовком
    `Next-Action`) получают 401, с пропуском POST проходит. Вход тестировщика: открытие
    страницы без пропуска — 303 на `/gate`, `WWW-Authenticate` нет; неверный логин или пароль и
    форма с чужого Origin пропуск не дают; поддельный и пустой пропуск — 401; верный вход ведёт
    на запрошенную страницу, и с пропуском она открывается.
    Набор вариантов не доказывает стойкость ко всем возможным каноникализациям URL.
  - `Lint, typecheck, test, build`: браузерный тест `scripts/landing-e2e.mjs` за настоящим
    `deploy/Caddyfile`: главная не делает запросов в закрытую часть, прелоадер скрыт через
    3,3 с, reduced motion; без пропуска закрытая страница уводит на `/gate` (ни 401, ни
    `WWW-Authenticate` по пути), неверный пароль показывает ошибку на странице, после входа
    открывается запрошенная страница; при остановленном Caddy и
    `navigator.onLine = true` показывается `/offline`. Тест проверен на двух неверных вариантах
    SW (обход SW по `navigator.onLine`): его он ловит.
- Тексты главной не обещают того, чего нет: функции помечены «Работает», «Частично» или
  «Скоро». Безопасная сделка и платежи в бете не реализованы (раздел 7), на главной они «Скоро».

## 9. Автообновление сервера

`deploy/autodeploy` (таймер systemd, `deploy/README.md`): сервер сам забирает новые коммиты
`main` из публичного репозитория и пересобирает стек. Модель доверия и ограничения:

- **Кто может менять прод**: любой, кто может попасть в `main`, получает выполнение кода на
  сервере (сборка образов и запуск контейнеров от root). Так было и при ручном `git pull`, но
  теперь без участия человека. Поэтому `main` меняется только через PR с аудитом и зелёным CI;
  рекомендуется защита ветки `main` в настройках GitHub (обязательный PR и проверки CI, запрет
  force-push).
- **Только строго зелёный CI** (`deploy/autodeploy/ci_gate.py`): workflow `ci.yml` для точного
  SHA завершён успешно и каждая обязательная задача — success. skipped, neutral, cancelled или
  отсутствующая задача — не зелёная; учитываются все страницы списка задач. Ошибки GitHub API
  (403/429/таймаут) и непонятный ответ — «ждать», а не «разворачивать». API без токена (лимит 60
  запросов в час на IP); запросы идут, только пока новый коммит ждёт развёртывания.
- **Только fast-forward**: локальные правки на сервере или переписанная история `main`
  останавливают обновление, ничего не перезаписывая.
- **Сборка отдельно от переключения**: пока образы собираются или если сборка упала, работают
  прежние контейнеры. `docker compose up` не атомарен: при сбое переключения часть контейнеров
  может быть новой — это ловит проверка здоровья.
- **Проверка здоровья после обновления**: контейнеры healthy; через Caddy по HTTPS главная 200,
  закрытая страница без пропуска 401, статика и кадры 200. Без неё коммит не записывается как
  развёрнутый; unit завершается с ошибкой; журнал содержит причину и указатель на runbook
  (`deploy/README.md`, «Если обновление не прошло»), без значений из `deploy/.env`.
- **Секретов нет**: сервер только читает публичный репозиторий; ключей доступа к серверу в
  GitHub нет, входящих подключений автообновление не требует.
- **Откат**: автоматического нет; миграции БД назад не откатываются без отдельного решения.
  Откат кода — revert через PR в `main`.
- **Известные риски, которые снимаются не кодом**:
  - автообновление и сборка идут от root (systemd unit, Docker); отдельный пользователь с
    доступом к Docker равносилен root, поэтому не вводится;
  - защита ветки `main` в GitHub (обязательный PR, обязательные проверки CI, запрет force-push)
    настраивается владельцем репозитория: без неё обход PR даёт выполнение кода на сервере;
  - резервные копии БД пока делаются вручную (`deploy/README.md`, «Полезные команды») и должны
    храниться вне сервера; проверка восстановления — в отдельную временную базу. Автоматические
    копии — отдельная задача.
- Проверка сценариев без сервера: `scripts/autodeploy-test.sh` (CI) — нет нового коммита, CI
  идёт, 429, чужой SHA и чужой workflow, только skipped, neutral, нет задачи, cancelled, красный
  CI, несколько страниц задач, ошибка сборки, частичный сбой переключения, повтор после
  исправления, сбой рестарта Caddy, главная 502 и 000, закрытая страница 200 вместо 401,
  недоступная статика, нездоровый контейнер, расхождение истории.
- Отчёт о сервере только для чтения: `deploy/autodeploy/inventory.sh` (SHA, `git status`,
  контейнеры и образы, таймер, журнал deploy.sh, DNS/HTTPS и ответы маршрутов, миграции).

## 10. Заявки на тестирование и персональные данные (152-ФЗ)

Форма на главной собирает имя и телефон. Это персональные данные, поэтому:

- **Приём выключен, пока нет реквизитов оператора.** `PRIVACY_OPERATOR` в
  `packages/shared/src/leads.ts` равен `null`: API отвечает 503 на `POST /v1/leads`, форма на
  главной видна, но выключена, а `/privacy` предупреждает, что реквизиты будут опубликованы.
  Включение — один коммит с реквизитами (ИП или организация, ИНН, ОГРН, email для обращений).
- **Согласие обязательно и записывается.** API требует `consent: true` (отдельная галочка со
  ссылкой на `/privacy`); вместе с заявкой хранится версия политики `PRIVACY_POLICY_VERSION`.
- **Хранится минимум:** имя, телефон в формате `+7XXXXXXXXXX` (CHECK в базе), время, версия
  согласия, отметка «обработана». IP в базу не пишется.
- **Защита от заливки.** Ловушка для ботов (скрытое поле `website`), общий write rate limit,
  повтор того же номера за сутки не создаёт запись, не больше 300 заявок в сутки на весь сайт.
  Проверка повтора и суточного лимита идёт под транзакционной advisory-блокировкой; тест
  параллельных заявок падает, если блокировку убрать (проверено мутацией).
- **Отправка с главной — не Server Action.** Форма отправляет JSON на `POST /lead` (Route
  Handler в web): проверка Origin, тело до 2 КБ. Без JS та же форма уходит обычной отправкой
  POST (`application/x-www-form-urlencoded`), ответ — переход на `/?lead=<код>#apply`: в адрес
  попадает только код результата, имя и телефон — никогда (аудит 23.10.2026; раньше форма без
  `method` ушла бы GET-запросом с телефоном в адресе, истории браузера и журналах прокси).
  Другие типы тела — 415. Это единственный
  POST, открытый в Caddy без пароля (раздел 8); остальные методы на открытых адресах закрыты.
- **Просмотр — только администратор.** `GET /v1/admin/leads` и `PATCH /v1/admin/leads/:id`:
  `SessionGuard` + роль `ADMIN`; отметка «обработана» и возврат пишутся в журнал аудита
  (`LEAD_PROCESSED`, `LEAD_REOPENED`). Страница `/admin/leads` за паролем Caddy.
- **Как назначается администратор.** Роль `ADMIN` нельзя выбрать при регистрации, и сервер
  никогда не выдаёт её сам: ни по email, ни при входе (email не подтверждается, поэтому не
  доказывает владение адресом; отрицательный e2e-тест в `leads.e2e-spec.ts`). Роль меняется
  только отдельной миграцией по известному ID аккаунта: владелец присылает номер из кабинета
  («ID 100245», столбец `users.public_id`; сам по себе номер доступа не даёт), миграция создаётся
  `node scripts/role-migration.mjs <номер|userId> ADMIN "<причина>"`, проходит PR и
  аудит и применяется автодеплоем. Она пишет в журнал аудита `USER_ROLE_CHANGED` со старой и
  новой ролью, повторный запуск ничего не меняет, отсутствующий аккаунт не вызывает ошибку
  (упавшая миграция остановила бы автодеплой). Снять роль — такой же миграцией с другой ролью.
- **Релизный гейт: включение приёма заявок.** `PRIVACY_OPERATOR` заполняется отдельным PR, и
  только после того, как выполнено всё ниже (до этого API отвечает 503):
  1. реквизиты оператора (наименование, ИНН, ОГРН, email для обращений) получены от владельца;
  2. текст `/privacy` и формулировка согласия проверены юристом, версия
     `PRIVACY_POLICY_VERSION` обновлена при любой правке текста;
  3. определён срок хранения заявок и способ удаления (по запросу субъекта и по окончании
     тестирования), назначен человек, который отвечает на обращения;
  4. оператор подал уведомление в Роскомнадзор, если оно требуется, или юрист подтвердил, что
     не требуется.
- Текст `/privacy` — шаблон по 152-ФЗ, составленный по фактической работе сервиса; это не
  юридическое заключение (см. релизный гейт выше).

## 11. Личный кабинет: профиль, фото, пароль, устройства, оформление

Все маршруты `/v1/me/*` берут пользователя только из сессии (`SessionGuard`), чужие данные по id
не адресуются.

- **Профиль** (`PATCH /v1/me`): имя, телефон (нормализуется в `+7XXXXXXXXXX`, CHECK в базе),
  город. Email и роль через этот маршрут не меняются: лишние поля отклоняются (whitelist DTO).
- **Фото** (`PUT/GET/DELETE /v1/me/avatar`): multipart в памяти, не больше 5 МБ (больше — 413).
  Формат определяется по содержимому, а не по расширению или Content-Type: только JPEG, PNG,
  WebP (SVG и прочее отклоняется). Картинка не больше 40 Мп, перекодируется sharp в WebP
  512×512; EXIF (геолокация, модель телефона) в результат не попадает (e2e проверяет и
  отсутствие EXIF, и отсутствие исходных байтов метаданных). Хранится в отдельной таблице
  `user_avatars` (до 512 КБ по CHECK), отдаётся только владельцу через `/account/avatar` web с
  `Cache-Control: private, no-cache` (картинка зависит от cookie, долгий кеш на общем компьютере
  показал бы её следующему пользователю) и `nosniff`. Загрузка через web: тело читается потоком
  с лимитом 5 МБ + 64 КБ до разбора multipart (Content-Length не нужен и не принимается на веру;
  тест проверяет, что чтение chunked-тела в 50 МБ прерывается сразу за лимитом). Второй рубеж:
  Caddy не передаёт web больше 8 МБ тела любого запроса (`request_body max_size`, ответ 413).
  `POST /lead` читает тело так же, с лимитом 2 КБ (тест и проверка chunked-тела в CI).
- **Пароль** (`POST /v1/me/password`): нужен текущий пароль; лимит как у входа (`auth`), чтобы
  смена не была способом перебора. Новый пароль: 10–128 символов, не равен текущему и email.
  После смены завершаются все остальные сеансы, текущий остаётся. В журнал аудита пишется
  `PASSWORD_CHANGED` без паролей и хешей.
- **Устройства** (`GET /v1/me/sessions`, `DELETE /v1/me/sessions/:id`,
  `POST /v1/me/sessions/revoke-others`): токены и их хеши не отдаются; удаление ищет сессию по
  id и пользователю сразу, поэтому чужую сессию не завершить и не обнаружить (404). Текущую так
  не закрыть (для неё есть выход). Подпись устройства («Chrome, Windows») строится из
  User-Agent браузера, который передаёт web (`X-Client-User-Agent`); полный User-Agent не
  хранится. Время активности обновляется не чаще раза в час. Завершения пишутся в аудит
  (`SESSIONS_REVOKED`).
- **Оформление** (`PATCH /v1/me/preferences`): тема, масштаб, анимации; значения из закрытых
  списков (DTO и CHECK в базе), применяются атрибутами на сервере в `(site)/layout.tsx`.
- Мутационные проверки: тест «чужая сессия» падает, если убрать `userId` из условия удаления;
  тест смены пароля падает, если смена завершает и текущий сеанс.

## 12. Вход через банк (Сбер ID, Т-Банк ID)

Код: `apps/api/src/oauth`, `apps/web/src/lib/bank-login.ts`, `apps/web/src/app/auth/[bank]`.
Тесты: `apps/api/test/oauth.e2e-spec.ts` (поддельный банк), `oauth.config.spec.ts`,
`apps/web/src/lib/bank-login.test.ts`.

- **Секреты только у API.** client_secret и сертификат Сбера лежат в окружении API и
  `deploy/secrets` (`deploy/docker-compose.bank-login.yml`); web получает от API готовый адрес
  страницы банка и передаёт API код из возврата. Обмен кода на токен и запрос данных человека
  идут с сервера: Сбер по mTLS с сертификатом клиента и проверкой цепочки УЦ Минцифры, Т-Банк с
  Basic-аутентификацией. Токены банка не хранятся, в журнал не пишутся (только банк и причина
  сбоя).
- **Подмена входа (login CSRF) и перехват кода.** При старте web кладёт в HttpOnly-cookie
  (SameSite=Lax, 10 минут, `__Host-` в production) случайные state, nonce и PKCE-verifier. Возврат
  принимается только с тем же state (сравнение за постоянное время), cookie удаляется сразу:
  чужая ссылка с кодом или повтор возврата не сработают. Сбер получает code_challenge (S256), API
  отдаёт code_verifier при обмене и проверяет в id_token aud (наш client_id) и nonce.
- **Адрес возврата** строит API из `OAUTH_REDIRECT_ORIGIN` (PUBLIC_ORIGIN), а не из запроса:
  подставить свой redirect_uri нельзя. Открытый редирект после входа закрыт той же проверкой
  `next`, что у входа по паролю (`safeRedirectPath`).
- **Аккаунт и email.** Человек определяется постоянным идентификатором банка (`sub`), связь —
  таблица `external_accounts` (уникальны пара банк+sub и банк на пользователя). Аккаунт с тем же
  email **автоматически не привязывается**: банк мог не подтвердить email, и это открыло бы
  чужой аккаунт. Владелец привязывает банк сам в настройках, войдя по паролю; привязать один
  банковский аккаунт к двум аккаунтам нельзя (409).
- **Новый аккаунт** создаётся с ролью заказчика или подрядчика (ADMIN отклоняется, как при
  регистрации). Если роль не выбрана, API возвращает «незавершённый вход», подписанный
  HMAC-SHA256 с ключом из секретов банков, на 15 минут; web хранит его в HttpOnly-cookie до выбора
  роли. Подделанный или просроченный — 410. Пароля у такого аккаунта нет (случайный argon2-хеш);
  вход по паролю для него появится вместе с восстановлением пароля.
- **Персональные данные.** Банк передаёт имя, email и телефон с согласия человека на стороне
  банка; сохраняются только они и `sub`. Требования 152-ФЗ к оператору (раздел 10) действуют и
  здесь: до реквизитов оператора и политики обработки вход через банк в бою не включать.
- **Сеть.** С `BANK_LOGIN=true` API получает выход в интернет (сеть `bank-egress`); других
  исходящих запросов у API нет, адреса банка задаются только окружением. Лимит `auth`
  (вход/регистрация) действует на все маршруты входа через банк.
- **Не подтверждено на настоящем банке.** Код проверен против поддельного банка по
  документации Сбер ID и T-ID; до включения нужна проверка на тестовом контуре Сбера
  (`id-ift.sber.ru`, адреса переопределяются `SBER_ID_*_URL`).
