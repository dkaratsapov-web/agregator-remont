# Готовность развёртывания (ТЗ #37, #40)

Что сделано в коде для надёжного обновления и восстановления сервера, что требует действий
владельца и что можно проверить только на VPS. Подробные команды — `deploy/README.md`.

## 1. Готово в коде (PR #39)

| Тема | Как устроено | Находки |
|---|---|---|
| Проверка после обновления | `/health/ready` с запросом к БД (503 при недоступной БД), healthcheck у api и Caddy, сравнение статусов без хвостовых пробелов | DEV-3, DEV-10 |
| Повтор и откат | до 3 попыток обновления; образы с тегом по SHA, хранятся 3 прошлых; `rollback.sh` — откат на прошлый SHA без пересборки | DEV-6, DEV-8 |
| Копии БД | ежедневно 03:17, перед каждой новой миграцией (без копии миграция не идёт), еженедельная проверка восстановления в контейнере без сети; хранение 14 дней | DEV-2 |
| Копия вне сервера | шифрование `age`, выгрузка `rclone`; включается настройками в `deploy/.env` | DEV-2 |
| Уведомления | Telegram и/или webhook: сбой обновления, красный CI, сбой копии, `OnFailure` всех служб, почасовая проверка | DEV-4 |
| Почасовая проверка | диск ≥ 80 %, сертификат < 14 дней, синхронизация времени, ответ сайта | DEV-9, DEV-12, DEV-15 |
| Место на диске | ротация логов Docker (10 МБ × 5), проверка ≥ 5 ГБ перед сборкой, чистка кеша сборки | DEV-9 |
| Секреты | вне образа (`.dockerignore`), `.env` и секреты с правами 600 | DEV-5, DEV-15 |
| Неизменяемые образы и действия CI | образы по digest, actions по коммиту | DEV-14 |
| Совместимые миграции | правило «сначала добавить, потом убрать», runbook P3009; CI сверяет схему и миграции; `migration-check.sh` разбирает новые миграции PR на операторы и пропускает только безопасные (пометка — на один оператор); обновление на данных прежнего формата и прежний API на новой схеме — в CI | DEV-7, ARCH-8, #40 п. 6 |
| Состояние копий (#40) | `backup-status`: `mode=local-only`, `offsite-size-checked` или `offsite-hash-checked` (размер и сумма в хранилище); копия вне сервера проверяется `restore-check.sh` по скачанному `.age`; `BACKUP_REQUIRE_OFFSITE=true` — без выгрузки сбой; `restore-status` после каждой проверки восстановления | #40 п. 2 |
| Наблюдаемость (#40) | почасовая проверка: возраст копии, local-only, давность и итог проверки восстановления, каналы уведомлений не заданы или отправка не дошла; `MONITOR_HEARTBEAT_URL` — пинг или `/fail` | #40 п. 3 |
| Предпроверки отката (#40) | `rollback.sh` отказывает без изменений: изменения или посторонние файлы в рабочей копии (в том числе игнорируемые по путям целевой версии), нет сохранённого SHA, Docker или база не отвечают, опасная миграция применена в базе; печатает порядок действий; флагов обхода нет | #40 п. 4 |
| Секреты в образах (#40) | CI подкладывает секреты в контекст сборки и проверяет файлы и историю собранных образов | #40 п. 5 |

Проверено автоматически: `scripts/autodeploy-test.sh` (123 проверки с заглушками git,
docker, age, rclone, curl), shellcheck всех скриптов (CI — версия Ubuntu), сборка и запуск
всего стека в Docker в CI (с Caddy и без). Учения `scripts/drills.sh` (задача CI «Disaster
drills», одноразовый стек раннера с Caddy): настоящие `pg_dump` и проверка восстановления
(число пользователей совпало с живой базой), обрезанная копия не проходит проверку, копия с
настоящими `age` и `rclone` выгружена, размер сверен, расшифрованная копия восстанавливается,
недоступное хранилище — сбой; сломанный релиз (API падает при старте) → `rollback.sh`: API
отвечает, данные на месте; миграция с `DROP COLUMN` применена к базе → откат отказан, стек не
тронут → по runbook копия перед миграцией восстановлена в живую базу → откат проходит, данные
на месте; копия вне сервера проверяется по скачанному `.age`.

Цели восстановления (предложение, утверждает владелец): закрытый тест — RPO 24 ч, RTO 4 ч;
публичный запуск — RPO ≤ 1 ч, RTO ≤ 2 ч (ежечасные копии или архив WAL — отдельная задача);
откат кода ≤ 15 мин. Что достигнуто сейчас: ежедневная копия (RPO до 24 ч) и копия перед
каждой миграцией; восстановление в учениях CI на пустом стеке — секунды, на VPS с реальным
объёмом не замерялось.

## 2. Нужны действия владельца

| Что | Зачем | Где |
|---|---|---|
| Защита ветки `main` (DEV-1, Critical) | сервер ставит любой зелёный коммит `main`: без защиты прямой push выполняет код на сервере | пошагово и с проверкой — `docs/BRANCH_PROTECTION.md` (4 обязательные проверки CI, пустой список обхода) |
| Хранилище копий вне сервера | без него копии погибнут вместе с сервером; до публичного запуска — обязательно (`BACKUP_REQUIRE_OFFSITE=true`, иначе копия — сбой) | `BACKUP_RCLONE_REMOTE`, `BACKUP_AGE_RECIPIENT`, `BACKUP_REQUIRE_OFFSITE` в `deploy/.env`; ключ хранилища — запись и список, без удаления и чтения |
| Канал уведомлений | без него о сбоях никто не узнает | `NOTIFY_TELEGRAM_TOKEN`, `NOTIFY_TELEGRAM_CHAT` или `NOTIFY_WEBHOOK_URL` |
| Внешний монитор и heartbeat | проверка «снаружи», если сервер целиком недоступен или не дошло уведомление | `MONITOR_HEARTBEAT_URL` (период 1 ч, допуск 1 ч), также `DEPLOY_`, `BACKUP_`, `RESTORE_HEARTBEAT_URL` (например, healthchecks.io) |
| RPO и RTO (DEV-13) | цели восстановления определяют частоту копий | предложение: тест — 24 ч / 4 ч; публичный запуск — ≤1 ч / ≤2 ч; откат кода ≤15 мин |
| Лимиты памяти и CPU (DEV-11) | сборка Next.js на сервере рядом с Postgres может вызвать OOM | нужны данные сервера: `free -h`, `nproc`, пик памяти при сборке |

## 3. Проверить на VPS после обновления

```bash
cd /opt/agregator   # каталог репозитория на сервере
# Статусы контейнеров (DEV-3: у caddy теперь healthcheck, строка без хвостового пробела)
docker compose -f deploy/docker-compose.yml -f deploy/docker-compose.proxy.yml \
  ps --format '{{.Service}} {{.State}} {{.Health}}' | cat -A
# Готовность API вместе с БД
docker compose -f deploy/docker-compose.yml -f deploy/docker-compose.proxy.yml \
  exec api node -e "fetch('http://localhost:4000/health/ready').then(r=>r.text()).then(console.log)"
# Журнал последнего обновления и история
journalctl -u agregator-deploy -n 50 --no-pager
tail -5 /var/lib/agregator-deploy/history
# Копия и проверка восстановления вручную, уведомление
sudo bash deploy/backup/backup.sh manual
sudo bash deploy/backup/restore-check.sh
sudo bash deploy/autodeploy/notify.sh "проверка уведомлений"
# Состояние копии, проверки восстановления и уведомлений (#40)
cat /var/lib/agregator-deploy/backup-status /var/lib/agregator-deploy/restore-status \
  /var/lib/agregator-deploy/notify-status
# Почасовая проверка вручную (пингует MONITOR_HEARTBEAT_URL)
sudo bash deploy/autodeploy/monitor.sh
# Таймеры
systemctl list-timers 'agregator-*'
```

Ожидаемо: db, api, web и caddy — `running healthy` (migrate завершён); `/health/ready` —
`{"status":"ok"}`; в журнале обновления нет повторов и сбоев, SHA в `history` — текущий
`main`; копия создана, проверка восстановления пишет число миграций
и время; уведомление пришло; в `backup-status` — `mode=offsite-hash-checked` или `offsite-size-checked` (до настройки
хранилища — `local-only`, и почасовая проверка об этом напоминает), в `restore-status` —
`result=ok`, в `notify-status` — `result=ok`; во внешнем мониторе появился пинг. Если что-то не так — `deploy/README.md`, раздел про сбои
обновления и P3009.

## 4. Риски, которые остаются

- Автообновление работает от root (известно, задокументировано в `SECURITY.md`).
- Один экземпляр API: счётчики лимитов в памяти, перезапуск обнуляет их.
- Новые миграции этого PR создают индексы без `CONCURRENTLY`: на текущем объёме это доли
  секунды, на миллионах заказов — блокировка записи на время построения.
- Вход через банк выключен; при включении нужен отдельный override с исходящим доступом к
  банкам (`docker-compose.bank-login.yml`).
