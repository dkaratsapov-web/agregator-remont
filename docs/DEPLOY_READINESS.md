# Готовность развёртывания (ТЗ #37)

Что сделано в коде для надёжного обновления и восстановления сервера, что требует действий
владельца и что можно проверить только на VPS. Подробные команды — `deploy/README.md`.

## 1. Готово в коде (PR #39)

| Тема | Как устроено | Находки |
|---|---|---|
| Проверка после обновления | `/health/ready` с запросом к БД (503 при недоступной БД), healthcheck у api и Caddy, сравнение статусов без хвостовых пробелов | DEV-3, DEV-10 |
| Повтор и откат | до 3 попыток обновления; образы с тегом по SHA, хранятся 3 прошлых; `rollback.sh` — откат на прошлый SHA без пересборки | DEV-6, DEV-8 |
| Копии БД | ежедневно 03:17, перед каждой новой миграцией (без копии миграция не идёт), еженедельная проверка восстановления в контейнере без сети; хранение 14 дней | DEV-2 |
| Копия вне сервера | шифрование `age`, выгрузка `rclone`; включается настройками в `deploy/.env` | DEV-2 |
| Уведомления | Telegram и/или webhook: сбой обновления, красный CI, сбой копии, `OnFailure` всех служб, почасовая проверка | DEV-4 |
| Почасовая проверка | диск ≥ 80 %, сертификат < 14 дней, синхронизация времени, ответ сайта | DEV-9, DEV-12, DEV-15 |
| Место на диске | ротация логов Docker (10 МБ × 5), проверка ≥ 5 ГБ перед сборкой, чистка кеша сборки | DEV-9 |
| Секреты | вне образа (`.dockerignore`), `.env` и секреты с правами 600 | DEV-5, DEV-15 |
| Неизменяемые образы и действия CI | образы по digest, actions по коммиту | DEV-14 |
| Совместимые миграции | правило «сначала добавить, потом убрать», runbook P3009; CI сверяет схему и миграции | DEV-7, ARCH-8 |

Проверено автоматически: `scripts/autodeploy-test.sh` (86 проверок с заглушками git и
docker), shellcheck всех скриптов, сборка и запуск всего стека в Docker в CI (с Caddy и без).

## 2. Нужны действия владельца

| Что | Зачем | Где |
|---|---|---|
| Защита ветки `main` (DEV-1, Critical) | сервер ставит любой зелёный коммит `main`: без защиты прямой push выполняет код на сервере | GitHub → Settings → Rules: только через PR, обязательны три проверки CI, запрет force-push и удаления |
| Хранилище копий вне сервера | без него копии погибнут вместе с сервером | `BACKUP_RCLONE_REMOTE`, `BACKUP_AGE_RECIPIENT` в `deploy/.env` |
| Канал уведомлений | без него о сбоях никто не узнает | `NOTIFY_TELEGRAM_TOKEN`, `NOTIFY_TELEGRAM_CHAT` или `NOTIFY_WEBHOOK_URL` |
| Внешний монитор и heartbeat | проверка «снаружи», если сервер целиком недоступен | `DEPLOY_HEARTBEAT_URL`, `BACKUP_HEARTBEAT_URL` (например, healthchecks.io) |
| RPO и RTO (DEV-13) | цели восстановления определяют частоту копий | предложение: тест — 24 ч / 4 ч; публичный запуск — ≤1 ч / ≤2 ч; откат кода ≤15 мин |
| Лимиты памяти и CPU (DEV-11) | сборка Next.js на сервере рядом с Postgres может вызвать OOM | нужны данные сервера: `free -h`, `nproc`, пик памяти при сборке |

## 3. Проверить на VPS после обновления

```bash
cd /opt/agregator   # каталог репозитория на сервере
# Статусы контейнеров (DEV-3: у caddy теперь healthcheck, строка без хвостового пробела)
docker compose -f deploy/docker-compose.yml -f deploy/docker-compose.proxy.yml \
  ps --format '{{.Service}} {{.State}} {{.Health}}' | cat -A
# Готовность API вместе с БД
docker compose -f deploy/docker-compose.yml -f deploy/docker-compose.proxy.yml \
  exec api node -e "fetch('http://localhost:4000/health/ready').then(r=>r.text()).then(console.log)"
# Журнал последнего обновления и история
journalctl -u agregator-deploy -n 50 --no-pager
tail -5 /var/lib/agregator-deploy/history
# Копия и проверка восстановления вручную, уведомление
sudo bash deploy/backup/backup.sh manual
sudo bash deploy/backup/restore-check.sh
sudo bash deploy/autodeploy/notify.sh "проверка уведомлений"
# Таймеры
systemctl list-timers 'agregator-*'
```

Ожидаемо: db, api, web и caddy — `running healthy` (migrate завершён); `/health/ready` —
`{"status":"ok"}`; в журнале обновления нет повторов и сбоев, SHA в `history` — текущий
`main`; копия создана, проверка восстановления пишет число миграций
и время; уведомление пришло. Если что-то не так — `deploy/README.md`, раздел про сбои
обновления и P3009.

## 4. Риски, которые остаются

- Автообновление работает от root (известно, задокументировано в `SECURITY.md`).
- Один экземпляр API: счётчики лимитов в памяти, перезапуск обнуляет их.
- Новые миграции этого PR создают индексы без `CONCURRENTLY`: на текущем объёме это доли
  секунды, на миллионах заказов — блокировка записи на время построения.
- Вход через банк выключен; при включении нужен отдельный override с исходящим доступом к
  банкам (`docker-compose.bank-login.yml`).
