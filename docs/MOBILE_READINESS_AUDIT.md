**Статус:** аналитика и проектирование. Runtime-код, схема БД и CI в этом PR не меняются.
**Основа:** `main` на коммите `0d2b56d` (Фазы 0, 1.1, 1.2, 1.3 и подготовка к домену).
Все пометки **[есть]** относятся к этому коммиту, а не к будущим веткам.
**Редакция 2** — после аудита PR #11.
**ТЗ:** `docs/MOBILE_READY_TZ.md` (PR #9).
**Связанные документы:** `docs/MOBILE_AUTH_DESIGN.md`, `docs/adr/0001`–`0005`.

Обозначения в документе: **[есть]** — реализовано и покрыто тестами на `main`;
**[нет]** — отсутствует; **[план]** — предлагается, требует отдельного PR и согласования.
Ничего из помеченного [план] не реализовано.

## 1. Краткий вывод

1. **Бизнес-правила уже живут в API и БД [есть].** Ownership, роли, статусы заказов и откликов,
   квоты, единственность выбранного исполнителя и журнал изменений проверяются NestJS и
   PostgreSQL. Web (Server Actions) — тонкий адаптер. Нативному приложению не придётся
   переносить логику из web: оно сможет вызывать тот же `/v1`.
2. **Главный блокер для native — аутентификация и доступность API снаружи [нет].**
   Сейчас API находится во внутренней docker-сети и доступен только web. Сессионный токен
   живёт 30 дней без ротации и отзывается только «текущий выход». Для мобильного клиента
   нужны публичный вход в API, короткий access token + ротация refresh, управление
   устройствами. Дизайн — `docs/MOBILE_AUTH_DESIGN.md`.
3. **Контракт API описан только в TypeScript [есть частично].** Типы в `packages/shared`
   пишутся вручную и с ответами API сверяются e2e-тестами. Спецификации OpenAPI нет, формат
   ошибок — стандартный NestJS без машинного `code`. Это закрывают PR B и PR C.
4. **Сейчас самое дешёвое время для несовместимых правок `/v1`.** Единственный потребитель
   API — наш web, который выкатывается из того же коммита. После выхода первой версии
   приложения в сторы старые версии будут жить месяцами, и любая правка контракта станет
   дорогой. Поэтому чистку контракта (ошибки, пагинация списка откликов, политика enum'ов)
   нужно закончить **до** первого мобильного релиза (ADR 0001).

## 2. Карта текущего API и его потребителей

Все маршруты, кроме `/health`, — под префиксом `/v1`. Глобально (`setup-app.ts`,
`app.module.ts`): `helmet`; `ValidationPipe` (`whitelist`, `forbidNonWhitelisted`,
`transform`); CORS-заголовки выдаются только origin'ам из `CORS_ORIGINS` (в compose — пустой
список, то есть никому) и только для методов `GET/HEAD/OPTIONS` — это ограничивает только
браузеры, не другие клиенты; глобальный `ThrottlerGuard`: лимит `default` 120/мин на IP для
всех маршрутов, кроме `/health` (`@SkipThrottle`), плюс `auth` и `write` на помеченных
маршрутах.

| Метод и путь | Доступ | Лимит | Ответ | Потребитель в web |
| --- | --- | --- | --- | --- |
| `GET /health` | публично | без лимита (`@SkipThrottle`) | `{status}` | healthcheck контейнера |
| `GET /v1/jobs?page&limit&category` | публично | default | `Paginated<JobDto>` | RSC `/`, `/jobs` (`getJobs`) |
| `GET /v1/jobs/:id` | публично | default | `JobDto` / 404 | RSC `/jobs/[id]` (`getJob`) |
| `POST /v1/auth/register` | публично | auth 10/мин | `AuthSessionDto` 201 / 409 | action `registerAction` |
| `POST /v1/auth/login` | публично | auth 10/мин | `AuthSessionDto` / 401 | action `loginAction` |
| `POST /v1/auth/logout` | сессия | default | 204 / 401 | action `logoutAction` |
| `GET /v1/me` | сессия | default | `UserDto` | `lib/session.ts` (`getMe`), все кабинеты |
| `GET /v1/me/jobs?page&limit` | CUSTOMER | default | `Paginated<OwnJobDto>` | RSC `/account/jobs` |
| `GET /v1/me/jobs/:id` | CUSTOMER, владелец | default | `OwnJobDto` / 404 | RSC `/account/jobs/[id]` |
| `POST /v1/me/jobs` | CUSTOMER | write 30/мин + 20/сутки | `OwnJobDto` 201 | action `createJobAction` |
| `PATCH /v1/me/jobs/:id` | CUSTOMER, владелец | write | `OwnJobDto` / 404 / 409 | action `updateJobAction` |
| `POST /v1/me/jobs/:id/close` | CUSTOMER, владелец | write | `OwnJobDto` / 409 | action `closeJobAction` |
| `GET /v1/me/profile` | CONTRACTOR | default | `ContractorProfileDto` | RSC `/account/profile` |
| `PUT /v1/me/profile` | CONTRACTOR | write | `ContractorProfileDto` | action `saveProfileAction` |
| `POST /v1/jobs/:jobId/bids` | CONTRACTOR | write + 30/сутки | `MyBidDto` 201 / 409 | action `placeBidAction` |
| `GET /v1/me/bids?page&limit&jobId` | CONTRACTOR | default | `Paginated<MyBidDto>` | RSC `/account/bids`, карточка заказа |
| `POST /v1/me/bids/:bidId/withdraw` | CONTRACTOR, автор | write | `MyBidDto` / 409 | action `withdrawBidAction` |
| `GET /v1/me/jobs/:jobId/bids` | CUSTOMER, владелец | default | **`JobBidDto[]` (массив)** | RSC `/account/jobs/[id]` |
| `POST /v1/me/jobs/:jobId/bids/:bidId/accept` | CUSTOMER, владелец | write | `JobBidDto` / 409 | action `acceptBidAction` |

Что уже независимо от web **[есть]**: все маршруты выше принимают `Authorization: Bearer`
и не зависят от cookie, заголовков Next.js или HTML-форм. e2e-тесты API (Jest + supertest)
вызывают их напрямую без web. Мобильный клиент мог бы пользоваться ими уже сейчас, если бы
API был доступен снаружи и существовал безопасный мобильный вход.

Чего нет **[нет]**: публичного адреса API, OpenAPI, машинных кодов ошибок, эндпоинтов
управления сессиями, refresh-токенов, проверки минимальной версии клиента.

## 3. Бизнес-правила: где они проверяются

### 3.1 Окончательные (серверные) правила — все в API/БД [есть]

| Правило | Где проверяется | Тесты |
| --- | --- | --- |
| Роль берётся из БД по сессии, не из запроса | `SessionGuard`, `RolesGuard` (fail closed) | `roles.spec.ts`, e2e |
| `ADMIN` не получить регистрацией | `RegisterDto` (`@IsIn`) | e2e auth |
| Владение заказом; чужой ресурс → 404 | `my-jobs.service` (`WHERE owner_id`) | e2e «А не видит Б» |
| Владение откликом; чужой → 404 | `bids.service` | e2e |
| Редактировать можно только `OPEN` заказ | `my-jobs.service` под `FOR UPDATE` | e2e, гонки |
| Откликаться можно только на `OPEN` заказ | `bids.service` под `FOR SHARE` | e2e, гонки |
| Один выбранный исполнитель на заказ | `FOR UPDATE` + частичный уникальный индекс `bids_one_accepted_per_job` | e2e, гонки |
| Один отклик подрядчика на заказ | уникальный индекс `(job_id, contractor_id)` | e2e |
| Квоты: 20 заказов и 30 откликов за сутки | сервис под блокировкой строки пользователя | e2e, гонки |
| Бюджет `min ≤ max`, длины, категории | DTO + сервис + CHECK в БД | e2e |
| Журнал изменений | та же транзакция, что и изменение | e2e |
| Лимиты частоты auth/write | `@nestjs/throttler` по IP | e2e `client-ip-rate-limit` |

### 3.2 Логика, которая живёт только в web — не бизнес-правила

| Что | Файл | Почему это не нужно переносить |
| --- | --- | --- |
| Разбор форм (`job-form.ts`, `bid-form.ts`), `isEntityId` | `apps/web/src/lib` | UX: ранние понятные ошибки. API повторяет проверку полностью. |
| Скрытие кнопок (отклик на закрытый заказ и т.п.) | страницы web | только интерфейс, API отклоняет запрос сам |
| CSRF для Server Actions (`isSameOriginRequest`, `WEB_PUBLIC_ORIGIN`) | `lib/same-origin.ts`, `lib/action-guard.ts` | защита именно браузерной cookie-сессии; native не использует cookie |
| Cookie `__Host-ar_session` | `lib/session.ts` | способ хранения токена в браузере |
| IP посетителя из `X-Forwarded-For` | `lib/client-ip.ts` | web — прокси для API; native будет ходить в API напрямую |
| Безопасный редирект после входа | `lib/redirect.ts` | навигация web |

**Вывод:** правил, которые проверяются только в web, не найдено. Риск на будущее — новые
функции, где проверку по ошибке сделают в Server Action. Это закрывается ADR 0004
(Server Actions — только адаптер) и требованием для каждого нового write-эндпоинта
(`docs/SECURITY.md`, раздел 6): тест «A не может читать/менять ресурс Б» на уровне API.

## 4. Инвентаризация контрактов

### 4.1 `packages/shared` [есть]

Собирается в CommonJS, без зависимостей от Next.js и `server-only`, импортируется и API, и web.

| Модуль | Экспорт |
| --- | --- |
| `jobs.ts` | `JOB_CATEGORIES` (с русскими названиями), `JOB_STATUSES`, `JobDto`, `OwnJobDto`, `JobInput`, `JOB_LIMITS`, `isJobCategory` |
| `pagination.ts` | `PAGINATION` (page ≤ 10000, limit ≤ 50), `Paginated<T>` = `{items, page, limit, total}` |
| `auth.ts` | `USER_ROLES`, `SELF_SERVICE_ROLES`, `AUTH_LIMITS`, `UserDto`, `AuthSessionDto` |
| `bids.ts` | `BID_STATUSES`, `BID_LIMITS`, `PROFILE_LIMITS`, `ContractorProfileDto/Input`, `BidInput`, `BidDto`, `MyBidDto`, `JobBidDto` |

Синхронность enum'ов Prisma и `shared` проверяется unit-тестом API. Соответствие интерфейсов
DTO реальным ответам проверяется e2e-тестами точечно (явные whitelist-мапперы
`toUserDto`, `bid.mapper.ts`, `profile.mapper.ts`), но **не машинно для всего API**.

Пригодность для React Native — **гипотеза, не проверено**: пакет не использует Node API и
Next.js, но собирается в CommonJS, и сборка в Metro/Expo не проверялась. Проверить
smoke-сборкой при старте мобильной разработки (ADR 0003). Русские названия категорий и
статусов в пакете допустимы (продукт русскоязычный); при локализации их понадобится
отделить от кодов.

### 4.2 Prisma [есть]

Модели: `Job`, `User`, `Session` (`tokenHash` char(64), `expiresAt`), `AuditLog`,
`ContractorProfile` (PK `userId`), `Bid`. Enum'ы: `JobCategory`, `JobStatus`, `Currency`,
`AuditAction`, `BidStatus`, `UserRole`. Миграции: `init`, `auth_users_sessions`,
`job_owner_audit_log`, `contractor_profiles_bids`.

Идентификаторы — `cuid` (подходят для deeplink'ов, не перечисляемы). Деньги — целые рубли
(`Int`), валюта `RUB`. Даты в API — ISO 8601 UTC.

### 4.3 Ошибки [есть частично]

Формат — стандартный NestJS: `{ statusCode, message, error }`, где `message` — строка, а для
ошибок валидации DTO — **массив строк**. Машинного `code` нет; клиент различает ситуации
только по статусу и русскому тексту. Web показывает `message` (или его первый элемент).

| Статус | Когда возникает сейчас |
| --- | --- |
| 400 | валидация DTO/query, «Нет полей для изменения», бюджет min > max |
| 401 | нет/недействительная сессия; неверный email или пароль |
| 403 | роль не подходит (`RolesGuard`) |
| 404 | ресурс не найден **или чужой** (намеренно не 403) |
| 409 | email занят; заказ не `OPEN`; отклик уже есть; отклик не на рассмотрении; заказ закрыт |
| 429 | rate limit (`ThrottlerException`) **и** суточные квоты (`HttpException 429`) |

Проблема для native: два разных 429 (повторить через минуту vs. квота на сутки) и пять
разных 409 неразличимы без разбора текста. Решение — ADR 0002 (PR C).

### 4.4 Пагинация и сортировка [есть частично]

- `GET /v1/jobs`, `/v1/me/jobs`, `/v1/me/bids` — `Paginated<T>`, сортировка
  `(createdAt desc, id desc)` — стабильная.
- **`GET /v1/me/jobs/:jobId/bids` возвращает массив без пагинации и без верхней границы**
  (сортировка `createdAt asc, id asc`). Количество откликов на заказ сейчас ограничено только
  числом подрядчиков. Для мобильного списка и для защиты от больших ответов нужно привести
  к `Paginated` до первого мобильного релиза (ADR 0001, P1).
- Offset-пагинация: при вставках между запросами возможны сдвиги. Для лент и чатов в Фазе 2
  — курсорная пагинация (ADR 0005). Для текущих списков offset допустим.
- Публичные списки не содержат приватных данных: `JobDto` без владельца и контактов,
  `JobBidDto` — имя и профиль подрядчика без email.

## 5. Модель сессии сейчас и что нужно мобильному клиенту

### 5.1 Сейчас [есть]

```
Браузер ──cookie __Host-ar_session (HttpOnly, Secure, SameSite=Lax)──▶ Next.js (RSC / Server Actions)
Next.js ──Authorization: Bearer <token>, X-Forwarded-For: <IP посетителя>──▶ NestJS API (внутренняя сеть)
NestJS: SHA-256(token) → sessions → users (роль из БД)
```

- Токен: 32 случайных байта (base64url), в БД только SHA-256, срок 30 дней, без продления.
- Выход удаляет текущую сессию. «Выйти везде», список устройств, отзыв при смене пароля —
  **[нет]** (это пункт 4 release gate в `docs/SECURITY.md`).
- CSRF неприменим к API (Bearer, не cookie); Server Actions защищены проверкой Origin.

### 5.2 Почему эту схему нельзя скопировать в приложение

- Нативному приложению не нужны cookie и Next.js-прокси: оно хранит секрет в системном
  хранилище и ходит в API напрямую. Пропускать мобильный трафик через web (Server Actions)
  — значит превратить BFF в публичный API без контракта.
- 30-дневный токен без ротации на устройстве, которое могут потерять, — слишком долгое окно
  при утечке.
- Без списка сессий пользователь не может отозвать потерянный телефон.

Рекомендуемая схема — opaque access token (короткий) + ротируемый refresh token с
детектированием повторного использования, сессии с типом клиента и устройством. Подробно —
`docs/MOBILE_AUTH_DESIGN.md`. **Web-схема (HttpOnly cookie) не меняется**; перевод web на
`localStorage` не рассматривается.

### 5.3 Доступ к API снаружи [нет]

Сейчас: `deploy/docker-compose.yml` держит API во внутренней сети `backend`, `CORS_ORIGINS`
пустой, `TRUST_PROXY` доверяет только статическому адресу web, а на домене весь сайт закрыт
basic auth Caddy (закрытая бета).

Для native понадобится [план]:
- публичный вход API через Caddy (поддомен `api.<домен>` или путь `/api`), без basic auth;
- `TRUST_PROXY` = адрес Caddy для этого входа (не web), отдельная проверка цепочки
  `X-Forwarded-For`;
- отдельные лимиты для мобильного входа и **распределённый** rate limit (Redis): у мобильных
  операторов много абонентов выходит в интернет с одного IP (CGNAT), поэтому лимиты только
  по IP дадут ложные 429 и не защитят от перебора (см. release gate 1–2);
- закрытая бета для приложения — через TestFlight/внутреннее тестирование Google Play и
  allowlist аккаунтов на сервере, а не через basic auth.

CORS при этом не меняется и **не считается защитой**: нативное приложение CORS не
проверяет вовсе, а защиту дают аутентификация, авторизация и лимиты на API.

## 6. Карта будущих модулей (Фаза 2+) — ничего из этого не реализовано

| Модуль | Сервер (API) | Web | Mobile | Решение |
| --- | --- | --- | --- | --- |
| Контакты | раскрытие контактов только участникам после выбора исполнителя, журнал | показ в кабинете | то же | ADR 0005 |
| Чат | диалоги, membership на сервере, идемпотентная отправка, курсорная пагинация, прочтения | polling | polling, затем push как сигнал | ADR 0005 |
| Файлы/фото | S3-совместимое хранилище, presigned URL после проверки доступа, MIME по сигнатуре | загрузка напрямую в S3 | то же | ADR 0005 |
| Уведомления | события домена → outbox → каналы (web, email, push) | in-app + email | push (FCM/APNs) после отдельного решения | ADR 0005 |
| Сделки | FSM + audit log на API, без денег | UI статусов | то же | ADR 0005; платежи — Фаза 3 |
| Устройства/сессии | `/v1/me/sessions`, регистрация push-токена в привязке к сессии | «Мои устройства» | то же | `MOBILE_AUTH_DESIGN.md` |

Межплатформенная граница: всё, что меняет данные или решает «можно ли», — только в API.
Клиенты (web, iOS, Android) отвечают за отображение, UX-валидацию и хранение своего секрета.

## 8. План миграций без нарушения совместимости

Принцип: каждая правка либо **аддитивная** (новое поле, новый маршрут, новый необязательный
параметр), либо выполняется, пока единственный клиент — наш web из того же коммита.
Rollback для каждого шага — откат PR; миграции БД только добавляющие.

### 9.1 Гейт «право, ПДн, безопасность» — до публичного запуска приложений

Не оценивается в днях разработки, пока не принята политика данных: объём работ зависит от
решений юриста и владельца. Входит:
- политика данных: что удаляется при удалении аккаунта, что обезличивается (заказы,
  отклики, которые видит другая сторона), сколько хранится журнал изменений (`audit_logs`
  ссылается на пользователя через `SetNull`);
- удаление аккаунта из приложения (требование App Store и Google Play) и из web;
- локализация ПДн (152-ФЗ), роль зарубежных push-провайдеров и аналитики, согласия
  пользователей, тексты политики и оферты;
- требования сторов к приложению (модерация пользовательского контента, жалобы, блокировка
  пользователей) — пересекается с release gate 8;
- обработка жалоб и abuse, сроки реакции.

Оценка разработки — после утверждения политики, отдельным пунктом плана.

## 10. Решения владельца

Принято владельцем (Issue #10, после merge PR #11): пункты 1–5 — как рекомендовано, со сроками
мобильной сессии 60 дней (скользящий) / 180 дней (абсолютный); адрес API — `api.<домен>`.
Пункты 6–7 остаются открытыми.


1. **Модель мобильной аутентификации**: opaque access 15 мин + строго одноразовый refresh
   без окна повтора (рекомендация) или JWT. См. `MOBILE_AUTH_DESIGN.md`, раздел 3.
2. **Адрес публичного API** для приложений: `api.<домен>` (рекомендация) или `<домен>/api`.
3. **Источник истины контракта**: код NestJS → OpenAPI → сгенерированные типы
   (рекомендация, ADR 0003) или ручные типы `shared` как сейчас.
4. **Формат ошибок** `{statusCode, code, message, error, fieldErrors?}` с сохранением `message`
   (ADR 0002).
5. **Срок «заморозки» `/v1`**: несовместимые правки допустимы только до первого
   мобильного релиза (ADR 0001).
6. **Технология приложений** (React Native + Expo по ТЗ) и момент создания `apps/mobile` —
   решение откладывается; папка в этом PR не создаётся.
7. **Политика данных** для гейта 9.1 (удаление аккаунта, хранение, 152-ФЗ) — с юристом.
