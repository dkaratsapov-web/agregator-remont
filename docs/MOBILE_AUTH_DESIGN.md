# Дизайн аутентификации для мобильных приложений

**Статус:** проект для согласования (PR A, Issue #10). **Ничего из этого документа не
реализовано.** Эндпоинты, миграции и клиентский код появятся только отдельным PR с тестами
и независимым security review, после утверждения модели владельцем.
Release gate аутентификации из `docs/SECURITY.md` (раздел 5) продолжает действовать.

---

## 1. Что не меняется

- **Web остаётся на текущей схеме**: токен в cookie `__Host-ar_session` (`HttpOnly`,
  `Secure`, `SameSite=Lax`), Server Actions с проверкой `Origin`, Next.js передаёт токен в
  API как `Authorization: Bearer`. Перевод web на `localStorage`/`sessionStorage` или
  выдача токена в JavaScript браузера не рассматриваются.
- Существующие `POST /v1/auth/register|login|logout`, `GET /v1/me`, `SessionGuard`,
  `RolesGuard` (роль из БД), проверки владения, лимиты и журнал изменений сохраняются.
- Пароли — argon2id, как сейчас.

## 2. Требования к мобильной схеме

1. Секреты на устройстве — только в системном защищённом хранилище.
2. Короткое окно при утечке access token; долгий вход без повторного ввода пароля.
3. Обнаружение повторного использования refresh token (украден и использован дважды).
4. Мгновенный отзыв: одно устройство, все устройства, при смене/сбросе пароля.
5. В БД только хеши токенов; токены не попадают в логи, аналитику, crash-отчёты, URL.
6. Пользователь видит свои устройства и может отозвать любое.
7. Web-сессии продолжают работать без изменений и без миграции данных.

## 3. Рекомендуемая модель: opaque access + ротируемый refresh

### 3.1 Почему opaque, а не JWT

| | Opaque (рекомендуется) | JWT |
| --- | --- | --- |
| Отзыв | мгновенный: каждый запрос проверяет сессию в БД | только после истечения или через denylist (то есть всё равно БД) |
| Роль | читается из БД на каждом запросе — как сейчас | зашита в токен до истечения: смена роли/блокировка запаздывает |
| Согласованность с web | та же модель, тот же `SessionGuard` | второй механизм проверки, ключи подписи, ротация ключей |
| Стоимость | 1 запрос по индексу на запрос API (уже есть для web) | без запроса к БД |

Нагрузка маркетплейса не требует stateless-проверки, а мгновенный отзыв и роль из БД — уже
принятые свойства системы. Поэтому JWT не нужен. **Решение владельца: подтвердить opaque.**

### 3.2 Токены

| Токен | Формат | Срок (предложение) | Где хранится |
| --- | --- | --- | --- |
| Access | `ar_at_` + 32 случайных байта base64url | 15 минут | память приложения; при необходимости Keychain/Keystore |
| Refresh | `ar_rt_` + 32 случайных байта base64url | 30 дней без использования (скользящий), максимум 90 дней от входа | только Keychain/Keystore |

- Префиксы позволяют находить утёкшие токены сканерами секретов и в логах и различать
  web-токен (без префикса) и мобильные токены в `SessionGuard`.
- В БД — SHA-256 от токена (токены высокоэнтропийные, медленный хеш не нужен), как сейчас.
- Через 90 дней от входа — повторный ввод пароля даже при активном использовании.

### 3.3 Модель данных [план, миграция только добавляющая]

```
sessions (существующая таблица; новые поля nullable / с default)
  + client_type     WEB | MOBILE           default WEB  (существующие строки — WEB)
  + device_name     varchar(100)  null      «iPhone Анны» — вводится клиентом, экранируется
  + platform        IOS | ANDROID null
  + last_used_at    timestamptz   null      обновляется не чаще раза в 5 минут
  + revoked_at      timestamptz   null
  + revoke_reason   LOGOUT | LOGOUT_ALL | PASSWORD_CHANGED | REFRESH_REUSE | ADMIN  null
  + absolute_expires_at timestamptz null    только для MOBILE
  token_hash        остаётся для web-сессий; для MOBILE — null (нужно снять NOT NULL)

session_tokens (новая)
  id, session_id → sessions (cascade), kind ACCESS | REFRESH,
  token_hash char(64) unique, expires_at,
  rotated_at null  (для REFRESH: когда обменян на новую пару),
  attempt_id null  (для REFRESH: attemptId запроса, которым он был обменян),
  parent_id  null  → session_tokens (refresh, при обмене которого выпущен этот токен),
  created_at
```

Строка `sessions` с `client_type = MOBILE` — это «устройство» и одновременно семейство
refresh-токенов. Все использованные refresh-хеши семейства хранятся до удаления сессии,
поэтому повторное использование любого старого refresh обнаруживается.

### 3.4 Эндпоинты [план]

| Метод и путь | Назначение |
| --- | --- |
| `POST /v1/auth/mobile/login` | `{email, password, device: {name, platform}}` → `{user, sessionId, accessToken, accessExpiresAt, refreshToken, refreshExpiresAt}` |
| `POST /v1/auth/mobile/register` | то же для регистрации (или общий register с параметром клиента — решается в PR) |
| `POST /v1/auth/token/refresh` | `{refreshToken, attemptId}` → новая пара; старый refresh помечается `rotated_at` |
| `POST /v1/auth/logout` | существующий: для мобильного access token отзывает всю сессию устройства |
| `GET /v1/me/sessions` | список своих сессий: id, тип клиента, устройство, платформа, `createdAt`, `lastUsedAt`, `current`; без IP и токенов |
| `DELETE /v1/me/sessions/:id` | отзыв своей сессии; чужая → 404 |
| `POST /v1/me/sessions/revoke-all` | отзыв всех сессий (опционально кроме текущей); требует повторного ввода пароля |

Токены передаются только в теле ответа и заголовке `Authorization`, никогда в URL.
Ответы с токенами — `Cache-Control: no-store`.

### 3.5 Ротация refresh и обнаружение повторного использования

В одной транзакции:

1. `SELECT … FROM sessions WHERE id = … FOR UPDATE` (порядок блокировок: session — первой,
   согласуется с графом из `docs/SECURITY.md` 6.3: сессия не участвует в существующих
   цепочках user → job → bid).
2. Найти `session_tokens` по хешу, `kind = REFRESH`.
3. Сессия отозвана, истекла (скользящий или абсолютный срок) или токен не найден → 401.
4. Токен уже обменян (`rotated_at` не null):
   - если обменян меньше 30 секунд назад **и** `attemptId` совпадает с первой попыткой —
     это повтор после потерянного ответа: выдать новую пару, а пару, выданную первой
     попыткой, пометить недействительной;
   - иначе — **повторное использование**: отозвать сессию целиком
     (`revoke_reason = REFRESH_REUSE`), записать событие в журнал, ответить 401.
     Владелец украденного токена и атакующий оба выходят из системы; пользователь входит
     заново паролем.
5. Иначе: пометить `rotated_at`, выпустить новые access и refresh, продлить скользящий срок.

Клиент выполняет refresh в одном потоке (single-flight): параллельные запросы с истёкшим
access ждут одного обновления, а не запускают несколько.

### 3.6 Проверка запроса

`SessionGuard` различает токены по префиксу: без префикса — текущая web-сессия по
`sessions.token_hash`; `ar_at_` — поиск в `session_tokens` (`kind = ACCESS`, не истёк) с
проверкой сессии (`revoked_at is null`, сроки). Refresh token в `Authorization` не
принимается никогда. Роль и пользователь — из БД, как сейчас.

## 4. Хранение на устройстве

- iOS: Keychain, `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` — не синхронизируется в
  iCloud и не переносится из резервной копии на другое устройство.
- Android: Android Keystore (через `expo-secure-store`, если выбран Expo).
- Запрещено: `AsyncStorage`, обычные файлы, логи, аналитика, crash-отчёты, deeplink-URL,
  буфер обмена, WebView с cookie.
- Вход — только нативная форма приложения к API. WebView сайта для входа не используется.
- Certificate pinning — не включать на старте (риск заблокировать всех пользователей при
  смене сертификата Let's Encrypt); вернуться к вопросу при появлении денег (Фаза 3).
- App Attest (iOS) / Play Integrity (Android) — P2, как дополнительный сигнал против
  ботов на входе, не замена паролю и лимитам.

## 5. Модель угроз

| Угроза | Мера | Остаточный риск |
| --- | --- | --- |
| Кража access token (лог, прокси, отладка) | срок 15 минут; не логируется; префикс для сканеров | окно до 15 минут или до отзыва сессии |
| Кража refresh token и его повтор | ротация + обнаружение повторного использования → отзыв всей сессии | если атакующий успеет обменять первым, легитимный клиент получит 401 при следующем обмене и сессия будет отозвана |
| Replay запроса | TLS; write-операции идемпотентны по смыслу (повторное создание отклика → 409); для новых операций — `Idempotency-Key` (ADR 0005) | — |
| Потеря/кража устройства | «Мои устройства» → отзыв; отзыв мгновенный, т.к. каждый запрос проверяет сессию | данные, уже показанные на экране |
| Компрометация устройства (root/jailbreak, вредонос) | системное хранилище, `ThisDeviceOnly`; полностью не защищается | атакующий с root действует от имени пользователя до отзыва |
| Выход на одном устройстве | `POST /v1/auth/logout` отзывает сессию; клиент стирает токены | — |
| Выход на всех устройствах | `revoke-all` с повторным вводом пароля | — |
| Смена/сброс пароля | отзыв всех сессий, кроме текущей (при сбросе — всех) | реализуется вместе с release gate 3–4 |
| Смена роли или блокировка | роль и статус читаются из БД на каждый запрос; блокировка отзывает все сессии | — |
| Перебор паролей с мобильного API | лимиты по IP **и** по аккаунту, общее хранилище счётчиков (release gate 1–2), отдельный throttler для мобильного входа и refresh | CGNAT: по одному IP много абонентов — поэтому нужны лимиты по аккаунту |
| Злоупотребление refresh (DoS по БД) | лимит на сессию и IP | — |
| Утечка ПДн в логах/аналитике | в логах только id сессии/пользователя, без email, токенов, имени устройства | — |
| Фишинговое приложение | официальные сторы, Universal Links / App Links с проверкой домена | вне контроля сервера |

## 6. Влияние на web и совместимость

- Существующие строки `sessions` получают `client_type = WEB`; их токены и срок не меняются.
- Новые поля nullable, новая таблица отдельная — откат PR не ломает web.
- «Мои устройства» и «выйти везде» становятся доступны и web-пользователям (закрывают
  release gate 4 частично).
- `SessionGuard` меняется: это изменение существующего guard, поэтому — отдельный PR с
  тестами всех путей (web-токен, mobile access, refresh в `Authorization`, отозванная,
  истёкшая сессия) и отдельным ревью, как требует Issue #10.

## 7. Тесты, обязательные для будущего PR

- Вход, обновление, выход; refresh после выхода → 401.
- Повторное использование refresh → 401 и отзыв всей сессии; запись в журнале.
- Повтор в пределах 30 секунд с тем же `attemptId` → новая пара; с другим → отзыв.
- Параллельные refresh одного токена → ровно один успешен (гонка под `FOR UPDATE`).
- Access token после отзыва сессии → 401 сразу, а не после истечения.
- Пользователь А не видит и не отзывает сессии Б (404).
- Refresh token в `Authorization` → 401.
- Истечение по скользящему и абсолютному сроку.
- Web-сессии работают без изменений (существующие e2e и интеграционные тесты зелёные).
- Ответы не содержат хешей, чужих сессий, IP; токены не попадают в логи.

## 8. Решения для владельца

1. Opaque access + ротируемый refresh (рекомендуется) или JWT.
2. Сроки: access 15 минут, refresh 30 дней скользящий, максимум 90 дней — подтвердить.
3. Окно повтора refresh 30 секунд — подтвердить.
4. Требовать пароль для «выйти на всех устройствах» — подтвердить.
5. Порядок: mobile auth реализуется только после PR B/C и вместе с release gate 1–4.
