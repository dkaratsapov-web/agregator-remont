# Дизайн аутентификации для мобильных приложений

**Статус:** проект для согласования (PR A, Issue #10), редакция 2 — после аудита PR #11.
**Ничего из этого документа не реализовано.** Эндпоинты, миграции и клиентский код появятся
только отдельным PR с тестами и независимым security review, после утверждения модели
владельцем. Release gate аутентификации из `docs/SECURITY.md` (раздел 5) продолжает действовать.

---

## 1. Что не меняется

- **Web остаётся на текущей схеме**: токен в cookie `__Host-ar_session` (`HttpOnly`,
  `Secure`, `SameSite=Lax`), Server Actions с проверкой `Origin`, Next.js передаёт токен в
  API как `Authorization: Bearer`. Перевод web на `localStorage`/`sessionStorage` или
  выдача токена в JavaScript браузера не рассматриваются.
- Существующие `POST /v1/auth/register|login|logout`, `GET /v1/me`, `SessionGuard`,
  `RolesGuard` (роль из БД), проверки владения, лимиты и журнал изменений сохраняются.
- Пароли — argon2id, как сейчас.

## 2. Требования к мобильной схеме

1. Секреты на устройстве — только в системном защищённом хранилище.
2. Короткое окно при утечке access token; долгий вход без повторного ввода пароля.
3. Обнаружение повторного использования refresh token (украден и использован дважды).
4. Мгновенный отзыв: одно устройство, все устройства, при смене/сбросе пароля.
5. В БД только хеши токенов; токены не попадают в логи, аналитику, crash-отчёты, URL.
6. Пользователь видит свои устройства и может отозвать любое.
7. Web-сессии продолжают работать без изменений и без миграции данных.
8. **Fail closed**: любая ошибка проверки (БД недоступна, неожиданное исключение) — отказ в
   доступе, никогда не «пропустить».

## 3. Рекомендуемая модель: opaque access + строго одноразовый refresh

### 3.1 Почему opaque, а не JWT

| | Opaque (рекомендуется) | JWT |
| --- | --- | --- |
| Отзыв | мгновенный: каждый запрос проверяет сессию в БД | только после истечения или через denylist (то есть всё равно БД) |
| Роль | читается из БД на каждом запросе — как сейчас | зашита в токен до истечения: смена роли/блокировка запаздывает |
| Согласованность с web | та же модель, тот же `SessionGuard` | второй механизм проверки, ключи подписи, ротация ключей |
| Стоимость | 1 запрос по индексу на запрос API (уже есть для web) | без запроса к БД |

Нагрузка маркетплейса не требует stateless-проверки, а мгновенный отзыв и роль из БД — уже
принятые свойства системы. **Решение владельца: подтвердить opaque.**

### 3.2 Выбранный протокол ротации: строгий single-use (вариант A)

**Каждый refresh token можно обменять ровно один раз. Любое повторное предъявление уже
обменянного refresh — повторное использование: сессия устройства отзывается целиком,
пользователь входит заново паролем.** Окна повтора, «восстановления» по идентификатору
попытки и других исключений из обнаружения нет.

Цена решения: если ответ на refresh потерялся в сети, клиент не знает новый refresh и при
следующем обмене предъявит старый — сессия будет отозвана, потребуется повторный вход.
Это редкий случай (обмен раз в 15 минут активной работы), и он безопасен по умолчанию.
Обоснование отказа от варианта B (восстановление после потерянного ответа) — в разделе 9.

### 3.3 Токены и сроки

| Токен | Формат | Срок (предложение) | Где хранится на устройстве |
| --- | --- | --- | --- |
| Access | `ar_at_` + 32 случайных байта base64url | 15 минут с выпуска, но не дольше срока сессии | память приложения |
| Refresh | `ar_rt_` + 32 случайных байта base64url | до `min(сейчас + 30 дней, абсолютный срок сессии)` | только Keychain/Keystore |
| Сессия устройства | строка `sessions` | абсолютный срок 90 дней от входа; скользящий — по сроку текущего refresh | — |

- Префиксы позволяют находить утёкшие токены сканерами секретов и различать web-токен
  (без префикса) и мобильные токены в `SessionGuard`.
- В БД — SHA-256 от токена (токены высокоэнтропийные, медленный хеш не нужен), как сейчас.
- Через 90 дней от входа — повторный ввод пароля даже при активном использовании.

### 3.4 Модель данных и ограничения БД [план, миграция только добавляющая]

```
sessions (существующая таблица; новые поля nullable / с default)
  + client_type          WEB | MOBILE       NOT NULL default WEB (существующие строки — WEB)
  + device_name          varchar(64)  null  только для отображения, см. 3.8
  + platform             IOS | ANDROID null
  + last_used_at         timestamptz  null  обновляется не чаще раза в 5 минут
  + revoked_at           timestamptz  null
  + revoke_reason        LOGOUT | LOGOUT_ALL | PASSWORD_CHANGED | REFRESH_REUSE | ADMIN  null
  + absolute_expires_at  timestamptz  null
  token_hash             становится nullable
  CHECK: (client_type = 'WEB'    AND token_hash IS NOT NULL AND absolute_expires_at IS NULL)
      OR (client_type = 'MOBILE' AND token_hash IS NULL     AND absolute_expires_at IS NOT NULL
          AND platform IS NOT NULL)
  CHECK: (revoked_at IS NULL) = (revoke_reason IS NULL)

session_tokens (новая)
  id          cuid
  session_id  → sessions ON DELETE CASCADE
  kind        ACCESS | REFRESH
  token_hash  char(64) UNIQUE
  expires_at  timestamptz NOT NULL
  rotated_at  timestamptz null           только REFRESH: когда обменян
  created_at  timestamptz NOT NULL
  CHECK: kind = 'REFRESH' OR rotated_at IS NULL
  UNIQUE (session_id) WHERE kind = 'ACCESS'                       — не больше одного access на сессию
  UNIQUE (session_id) WHERE kind = 'REFRESH' AND rotated_at IS NULL — не больше одного живого refresh
  INDEX  (session_id, kind)
```

Пояснения:
- Строка `sessions` с `client_type = MOBILE` — это «устройство» и одновременно семейство
  refresh-токенов.
- **Обменянные refresh-хеши хранятся до удаления сессии**, поэтому повторное использование
  любого старого refresh этой сессии обнаруживается, пока сессия существует.
- Access token один на сессию: при ротации прежний access удаляется в той же транзакции.
- Очистка: периодическая задача удаляет сессии, у которых истёк абсолютный срок или
  которые отозваны более 30 дней назад; токены удаляются каскадно (это же закрывает
  release gate 5). Предъявление токена удалённой сессии — обычный 401 (сессия и так мертва).

### 3.5 Жизненный цикл (state machine)

```
Сессия:   ACTIVE ──logout / revoke / revoke-all / смена пароля / reuse / admin──▶ REVOKED (конечное)
          ACTIVE ──истёк refresh или абсолютный срок (по времени)──────────────▶ EXPIRED (вычисляется)
Refresh:  ACTIVE ──обмен──▶ ROTATED (конечное; повторное предъявление = reuse)
Access:   ACTIVE ──15 минут / ротация / отзыв сессии──▶ недействителен
```

Инварианты (проверяются тестами и ограничениями БД):
1. У активной сессии не больше одного живого refresh и одного access.
2. Ни один токен не действует, если сессия `REVOKED` или `EXPIRED`.
3. `ROTATED` и `REVOKED` не возвращаются в активное состояние.
4. Все изменения сессии и её токенов выполняются под `SELECT … FROM sessions … FOR UPDATE`.

### 3.6 Протокол обмена `POST /v1/auth/token/refresh`

Тело: `{ "refreshToken": "ar_rt_…" }`. Одна транзакция:

1. Найти `session_tokens` по `SHA-256(refreshToken)`, `kind = REFRESH`. Не найден → 401
   `UNAUTHENTICATED` (без подробностей).
2. `SELECT … FROM sessions WHERE id = <session_id> FOR UPDATE`, затем **перечитать** строку
   refresh-токена под этой блокировкой: решения шагов 3–6 принимаются только по данным,
   прочитанным после блокировки.
3. Сессия `REVOKED` или `EXPIRED` → 401.
4. Токен `ROTATED` → **повторное использование**: `revoked_at = now()`,
   `revoke_reason = REFRESH_REUSE`, удалить access сессии, запись в `audit_logs`, 401.
5. `expires_at` refresh прошёл → 401.
6. Иначе: `rotated_at = now()` для текущего refresh; удалить текущий access; создать новый
   access и новый refresh (`expires_at` по 3.3); `last_used_at = now()`; ответ
   `{accessToken, accessExpiresAt, refreshToken, refreshExpiresAt}`, `Cache-Control: no-store`.

Шаг 4 и шаг 6 выполняются под одной блокировкой строки сессии, поэтому два одновременных
обмена одного refresh упорядочены: первый получает новую пару, второй видит `ROTATED` и
отзывает сессию.

Порядок блокировок: `users` (если операция затрагивает пользователя) → `sessions` →
`session_tokens`. Сессии не участвуют в существующих цепочках `users → jobs → bids`
(`docs/SECURITY.md` 6.3), поэтому новых циклов не появляется.

### 3.7 Последовательности

**Нормальная ротация**

```
Клиент                         API                                   БД
  │ refresh(R1)                 │                                     │
  │────────────────────────────▶│ lock session; R1 ACTIVE             │
  │                             │ R1→ROTATED; del A1; ins A2, R2      │
  │◀──── {A2, R2} ──────────────│ commit                              │
  │ сохранить R2 в Keychain, затем использовать A2                    │
```

**Два одновременных обмена одного R1 (ошибка клиента: нет single-flight)**

```
Запрос X: refresh(R1) ─▶ lock ─▶ R1 ACTIVE ─▶ ROTATED, выдать A2/R2 ─▶ commit
Запрос Y: refresh(R1) ─▶ ждёт lock ───────────────────────────────▶ R1 ROTATED ─▶ REUSE:
                                                                     сессия REVOKED, 401
Итог: сессия отозвана, A2/R2 больше не действуют, пользователь входит паролем.
```

Поэтому клиент обязан выполнять обмен строго в одном потоке на устройство (single-flight
с межпроцессной блокировкой, если у приложения есть фоновые задачи или расширения).

**Потерянный ответ**

```
Клиент: refresh(R1) ─▶ API: R1→ROTATED, выдал A2/R2 ─▶ ответ потерян в сети
Клиент (позже): refresh(R1) ─▶ API: R1 ROTATED ─▶ REUSE: сессия REVOKED, 401
Клиент: стирает токены, показывает экран входа.
```

Осознанная цена варианта A (раздел 3.2).

**Атакующий украл R1**

```
Случай 1 — атакующий обменял первым:
  Атакующий: refresh(R1) ─▶ получает A2/R2
  Клиент:    refresh(R1) ─▶ R1 ROTATED ─▶ REUSE: сессия REVOKED (A2/R2 атакующего тоже), 401
Случай 2 — клиент обменял первым:
  Клиент:    refresh(R1) ─▶ получает A2/R2
  Атакующий: refresh(R1) ─▶ REUSE: сессия REVOKED, 401; клиент входит паролем
```

В обоих случаях окно атакующего ограничено временем до следующего обмена легитимного
клиента (не больше 15 минут активной работы или до открытия приложения), а также сроком
access (15 минут). Отзыв мгновенный, так как каждый запрос проверяет сессию.

### 3.8 Эндпоинты [план]

| Метод и путь | Назначение |
| --- | --- |
| `POST /v1/auth/mobile/login` | `{email, password, device: {name, platform}}` → `{user, sessionId, accessToken, accessExpiresAt, refreshToken, refreshExpiresAt}` |
| `POST /v1/auth/mobile/register` | то же для регистрации (или общий register с параметром клиента — решается в PR) |
| `POST /v1/auth/token/refresh` | протокол 3.6 |
| `POST /v1/auth/logout` | существующий: для мобильного access token отзывает всю сессию устройства |
| `GET /v1/me/sessions` | список своих сессий: id, тип клиента, устройство, платформа, `createdAt`, `lastUsedAt`, `current`; без IP и токенов |
| `DELETE /v1/me/sessions/:id` | отзыв своей сессии; чужая → 404 |
| `POST /v1/me/sessions/revoke-all` | отзыв всех сессий (опционально кроме текущей); требует повторного ввода пароля |

- Токены передаются только в теле ответа и заголовке `Authorization`, никогда в URL.
- `device.name` и `device.platform` — **недоверенные данные клиента**: длина до 64 символов,
  только печатные символы, `platform` строго из списка; используются только для показа
  пользователю в «Моих устройствах», никогда для решений о доступе. Экранируются при выводе.
- Отзыв (`logout`, `DELETE`, `revoke-all`, смена пароля) берёт ту же блокировку строки
  сессии, что и refresh: отзыв и обмен не могут пересечься. `revoke-all` и смена пароля
  блокируют строку пользователя, затем сессии в порядке `id`.

### 3.9 Проверка запроса (`SessionGuard`)

- Без префикса — текущая web-сессия по `sessions.token_hash` (без изменений поведения).
- `ar_at_` — поиск в `session_tokens` (`kind = ACCESS`, `expires_at > now()`) с проверкой
  сессии (`revoked_at IS NULL`, `absolute_expires_at > now()`).
- `ar_rt_` в `Authorization` — всегда 401.
- Роль и пользователь — из БД, как сейчас. Кэша сессий в памяти нет.
- Ошибка БД или любое исключение при проверке — запрос отклоняется (5xx), а не пропускается.
  Тест: при недоступной БД защищённые маршруты не возвращают 2xx.
- Запросы, начатые с прежним access до ротации, получат 401: клиент повторяет их **один
  раз** с текущим access, если тот уже сменился, и не запускает новый обмен.

## 4. Хранение на устройстве

- iOS: Keychain, `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` — не синхронизируется в
  iCloud и не переносится из резервной копии на другое устройство.
- Android: Android Keystore (через `expo-secure-store`, если выбран Expo).
- Новый refresh записывается в хранилище **до** использования нового access.
- Запрещено: `AsyncStorage`, обычные файлы, логи, аналитика, crash-отчёты, deeplink-URL,
  буфер обмена, WebView с cookie.
- Вход — только нативная форма приложения к API. WebView сайта для входа не используется.
- Certificate pinning — не включать на старте (риск заблокировать всех пользователей при
  смене сертификата Let's Encrypt); вернуться к вопросу при появлении денег (Фаза 3).
- App Attest (iOS) / Play Integrity (Android) — P2, как дополнительный сигнал против
  ботов на входе, не замена паролю и лимитам.

## 5. Модель угроз

Атакующие: (а) читает трафик/логи/бэкапы, где мог оказаться токен; (б) имеет копию
refresh token; (в) контролирует устройство (root/jailbreak, вредонос); (г) перебирает пароли
с многих адресов; (д) — легитимный клиент с ошибкой (параллельные обмены).

| Угроза | Мера | Остаточный риск |
| --- | --- | --- |
| Кража access token (лог, прокси, отладка) | срок 15 минут; один access на сессию; не логируется; префикс для сканеров | окно до 15 минут или до отзыва сессии |
| Кража refresh token и его повтор | строгая одноразовость; повтор любого обменянного refresh → отзыв всей сессии (3.7) | атакующий действует до следующего обмена легитимного клиента |
| Кража refresh token, который клиент ещё не обменял, и клиент неактивен | refresh истекает через 30 дней; «Мои устройства» и отзыв; уведомление о входе с нового устройства — P2 | до 30 дней при полностью неактивном клиенте |
| Replay запроса | TLS; повторное создание отклика → 409; для новых операций — `Idempotency-Key` (ADR 0005) | — |
| Потеря/кража устройства | «Мои устройства» → отзыв; отзыв мгновенный | данные, уже показанные на экране |
| Компрометация устройства | системное хранилище, `ThisDeviceOnly`; полностью не защищается | атакующий с root действует от имени пользователя до отзыва |
| Выход на одном устройстве | `logout` отзывает сессию; клиент стирает токены | — |
| Выход на всех устройствах | `revoke-all` с повторным вводом пароля | — |
| Смена/сброс пароля | в одной транзакции со сменой пароля отзываются все сессии (при смене — кроме текущей, при сбросе — все) | реализуется вместе с release gate 3–4 |
| Смена роли или блокировка | роль и статус читаются из БД на каждый запрос; блокировка отзывает все сессии | — |
| Перебор паролей с мобильного API | лимиты по IP **и** по аккаунту, общее хранилище счётчиков (release gate 1–2), отдельный throttler для мобильного входа и refresh | CGNAT: по одному IP много абонентов — поэтому нужны лимиты по аккаунту |
| Злоупотребление refresh (нагрузка на БД) | лимит на сессию и IP | — |
| Подмена `device_name`/`platform` | недоверенные данные, только для показа, экранирование | пользователь может назвать устройство как угодно |
| Ошибка клиента: параллельные обмены | single-flight на клиенте; на сервере — отзыв сессии (безопасно) | лишний повторный вход |
| Сбой БД во время проверки | fail closed: отказ, а не пропуск | недоступность сервиса на время сбоя |
| Утечка ПДн в логах/аналитике | в логах только id сессии/пользователя, без email, токенов, имени устройства | — |

## 6. Влияние на web и совместимость

- Существующие строки `sessions` получают `client_type = WEB`; их токены и срок не меняются.
- Новые поля nullable, новая таблица отдельная — откат PR не ломает web.
- «Мои устройства» и «выйти везде» становятся доступны и web-пользователям (закрывают
  release gate 4 частично).
- `SessionGuard` меняется: это изменение существующего guard, поэтому — отдельный PR с
  тестами всех путей и отдельным ревью, как требует Issue #10.

## 7. Тесты, обязательные для будущего PR

- Вход, обмен, выход; обмен после выхода → 401.
- Повторное предъявление обменянного refresh → 401, сессия `REVOKED` с `REFRESH_REUSE`,
  новые access/refresh тоже недействительны, запись в журнале.
- Повтор **более старого** refresh (R1 после R2 → R3) → то же.
- Параллельные обмены одного refresh → ровно один успешен, сессия отозвана (гонка под
  `FOR UPDATE`, тест в стиле существующих `*-concurrency.e2e-spec.ts`).
- Гонки: refresh vs logout, refresh vs revoke-all, refresh vs смена пароля — после отзыва
  ни один токен не действует, независимо от порядка.
- Ограничения БД: вторая живая пара в одной сессии не вставляется (unique partial index).
- Access token после отзыва сессии → 401 сразу; прежний access после ротации → 401.
- Пользователь А не видит и не отзывает сессии Б (404).
- Refresh token в `Authorization` → 401.
- Истечение по сроку refresh и по абсолютному сроку сессии.
- Очистка: удаление старых сессий не нарушает обнаружение повтора для живых сессий.
- Fail closed: при недоступной БД защищённые маршруты и refresh не возвращают 2xx.
- Web-сессии работают без изменений (существующие e2e и интеграционные тесты зелёные).
- Ответы не содержат хешей, чужих сессий, IP; токены не попадают в логи.

## 8. Решения для владельца

1. Opaque access + строго одноразовый refresh (рекомендуется) или JWT.
2. Сроки: access 15 минут, refresh 30 дней, абсолютный срок сессии 90 дней — подтвердить.
3. Принять цену варианта A: потерянный ответ на refresh приводит к повторному входу.
4. Требовать пароль для «выйти на всех устройствах» — подтвердить.
5. Порядок: mobile auth реализуется только после PR B/C и вместе с release gate 1–4.

## 9. Рассмотренные и отклонённые варианты

- **Окно повтора с идентификатором попытки (`attemptId`), редакция 1 этого документа.**
  Отклонено по итогам аудита: в БД хранятся только хеши, поэтому сервер не может вернуть уже
  выданную пару и должен выпускать ещё одну; идентификатор попытки — данные клиента, он
  передаётся вместе с refresh и может быть украден вместе с ним, то есть не доказывает
  легитимность и превращает окно в исключение из обнаружения повтора.
- **Вариант B: безопасное восстановление после потерянного ответа** (хранить результат
  обмена в зашифрованном виде на короткое время или привязать токены к ключу устройства —
  DPoP/подпись запросов ключом из Secure Enclave/StrongBox). Возможен, но требует отдельной
  криптографической схемы, хранения секретов результата и собственного аудита. Вернуться,
  если доля повторных входов из-за потерянных ответов окажется заметной по метрикам;
  оформить отдельным ADR.
- **JWT access token** — см. 3.1.
- **Долгий access без refresh** (как web, 30 дней) — слишком большое окно при утечке с
  устройства.
